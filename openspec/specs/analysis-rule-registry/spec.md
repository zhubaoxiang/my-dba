## Requirements
### Requirement: 规则的代码声明

每条分析规则 MUST 以声明方式在代码中定义，至少包含：稳定的字符串 `code`、名称、说明、默认严重级别、适用层级、默认阈值与判定函数。声明 MUST 是规则默认值的唯一来源；规则判定逻辑 MUST 是代码，MUST NOT 通过表达式、脚本或配置动态求值。

#### Scenario: 新增规则只改一处

- **WHEN** 开发者新增一条分析规则
- **THEN** 只需新增判定函数并追加一条规则声明，无需修改 `analyze()` 的方法调用列表

#### Scenario: 声明提供默认值

- **WHEN** 某条规则在规则注册表中没有对应记录
- **THEN** 分析时使用该规则声明中的默认启用状态、默认级别与默认阈值

#### Scenario: 规则标识稳定可读

- **WHEN** 查看规则清单或问题记录
- **THEN** 每条规则以其字符串 `code` 与名称标识，`code` 不随规则增删而改变

### Requirement: 规则可覆盖项持久化

系统 SHALL 持久化每条规则的可覆盖项：启用开关、严重级别、阈值。可覆盖项 MUST 以规则 `code` 为唯一键存储，MUST 支持运行时修改且无需重启服务。

#### Scenario: 修改启用开关立即生效

- **WHEN** 某条规则被停用后再执行分析
- **THEN** 该规则不产出任何新问题，其余规则照常产出，无需重启服务

#### Scenario: 修改级别立即生效

- **WHEN** 某条规则的严重级别被调整后再执行分析
- **THEN** 该规则新产出的问题使用新的严重级别，无需修改代码

#### Scenario: 阈值按规则独立

- **WHEN** 调整某条规则的阈值
- **THEN** 其他规则的阈值不受影响

#### Scenario: 覆盖项不因同步被重置

- **WHEN** 规则同步执行后，某条规则的启用开关或级别曾被人工修改
- **THEN** 这些人工修改 MUST 被保留，不因同步而回退为代码默认值

### Requirement: 规则管理接口

系统 SHALL 提供规则清单查询与管理接口：规则清单 MUST 以**代码声明为基底**、叠加库中已存的覆盖项后返回，使从未落库的规则也出现在清单中并展示代码默认值；MUST 支持修改启用状态、修改级别、修改阈值、恢复默认。规则 MUST 以其 `code` 定位，MUST NOT 依赖数据库自增主键。列表查询 MUST 分页。

#### Scenario: 查询规则清单（含尚未落库的规则）

- **WHEN** 请求规则清单，且某条规则在库中没有任何记录
- **THEN** 该规则 MUST 出现在清单中，其级别、启用状态与阈值取自代码声明

#### Scenario: 清单反映人工调整

- **WHEN** 某条规则的级别已被人工调整后请求规则清单
- **THEN** 该规则展示调整后的值，并标明该规则已被调整

#### Scenario: 修改启用状态

- **WHEN** 请求停用某条规则
- **THEN** 该规则记录被更新为停用状态，接口返回成功

#### Scenario: 修改为非法级别

- **WHEN** 请求把某条规则的级别设为不存在的档位
- **THEN** 系统返回参数错误（code 4000），规则不被修改

#### Scenario: 修改阈值格式非法

- **WHEN** 请求提交的阈值不是合法的键值结构
- **THEN** 系统返回参数错误（code 4000），规则不被修改

#### Scenario: 使用不存在的规则代码

- **WHEN** 请求操作一个不在代码声明中的规则 `code`
- **THEN** 系统返回资源不存在（code 4004）

### Requirement: 停用规则不影响历史问题

停用某条规则 MUST NOT 删除或修改任何已生成的问题记录。历史问题 MUST 能独立于规则注册表的当前状态正确展示。

#### Scenario: 停用后历史问题仍可查

- **WHEN** 某条规则被停用后查询该规则此前产出的问题
- **THEN** 问题记录仍可查询，且带有该规则当时的名称

#### Scenario: 规则改名后历史问题仍正确展示

- **WHEN** 某条规则在代码中被改名并同步后，查询此前产出的问题
- **THEN** 历史问题展示的是产出时记录的名称，不随规则改名而变化

#### Scenario: 停用规则不产出新问题

- **WHEN** 某条规则被停用后对某数据源重新采集
- **THEN** 新快照的问题清单中不含该规则的问题

### Requirement: 规则管理界面

系统 SHALL 提供前端页面用于查看与调整规则，页面 MUST 在同一处呈现**库表分析规则**与 **SQL 分析规则**两组清单，并显示各自的规则条数。两组 MUST 都给出每条规则的说明。库表规则组 MUST 提供启用开关、级别调整与阈值编辑入口；SQL 规则组 MUST 只读展示。一组内不具备的能力 MUST NOT 以禁用（置灰）控件伪装。

#### Scenario: 两组规则同页可见

- **WHEN** 用户进入规则页面
- **THEN** 页面同时提供库表分析规则与 SQL 分析规则的清单，并显示各自的规则条数

#### Scenario: 两组都给出说明

- **WHEN** 用户查看任一组规则
- **THEN** 每条规则 MUST 展示其说明；说明过长时可省略显示，但 MUST 能查看全文

#### Scenario: 库表规则可调整

- **WHEN** 用户在库表规则组中停用某条规则
- **THEN** 页面反映该规则已停用，后续分析不再产出该规则的问题

#### Scenario: SQL 规则只读

- **WHEN** 用户查看 SQL 规则组
- **THEN** 该组展示标识、名称、说明、级别与是否需要表结构，MUST NOT 出现启用开关或级别调整控件

### Requirement: 分析规则按层级适用

每条规则 MUST 声明其适用层级（库 / 模式 / 表 / 列）。系统 MUST 校验规则产出的问题层级与其声明的适用层级一致；不一致时 MUST 记录日志并跳过该条问题，MUST NOT 静默接受。

#### Scenario: 层级一致的规则正常产出

- **WHEN** 一条声明为表级的规则产出表级问题
- **THEN** 该问题正常写入问题清单并带有表级标识

#### Scenario: 层级不一致时跳过并留痕

- **WHEN** 一条声明为表级的规则产出了库级问题
- **THEN** 该条问题被跳过、记录日志，其余问题不受影响

#### Scenario: 支持非表级问题

- **WHEN** 一条声明为库级或模式级的规则产出问题
- **THEN** 该问题能被写入与查询，且不要求关联到具体表或列

### Requirement: 规则恢复默认

系统 SHALL 提供将单条规则的可覆盖项恢复为代码默认值的能力。系统 MUST NOT 要求任何「同步」动作作为查看或调整规则的前置条件。

#### Scenario: 恢复默认

- **WHEN** 对某条已人工修改的规则执行恢复默认
- **THEN** 该规则的启用开关、级别与阈值回到代码声明的默认值

#### Scenario: 未落库的规则无可恢复项

- **WHEN** 对一条从未被修改过（库中无记录）的规则执行恢复默认
- **THEN** 系统返回参数错误，且 MUST NOT 产生任何数据库记录

#### Scenario: 无需同步即可查看全部规则

- **WHEN** 查看规则清单，且从未执行过任何同步动作
- **THEN** 清单 MUST 展示全部规则及其代码默认值
