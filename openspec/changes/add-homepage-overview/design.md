## Context

前置状态：

- 首页是脚手架模板留下的假内容：三张写死的数字卡（用户总数 / 文档数量 / 待办通知）、一句「脚手架已就绪」、一个「测试后端接口连通性」按钮，全部与业务无关
- 系统已实现四条能力中的三条：**分析数据库表**、**知识问答**、**分析 SQL**（另有一条未开始）
- 其中**只有两条有数据沉淀**：库表分析（数据源 + 采集快照 + 问题清单）、知识问答（知识库 + 文档 + 会话）。**SQL 分析刻意不落库**，没有历史可展示
- 接口不做应用层鉴权（`AnyLogin`），访问控制依赖网络隔离
- 矢量检索由独立的 Qdrant 服务承载，Qdrant 客户端的超时取的是 `knowledge_llm_timeout`（**默认 60 秒**）

## Goals / Non-Goals

- **Goals**：让使用者打开系统第一眼就知道「**我该关注什么**」与「**为什么某个功能用不了**」；每条信息都能点进去处理
- **Non-Goals**：不做任务入口卡片墙；不做图表与趋势；不展示 SQL 分析的任何数据；不探测外部服务可用性；不做自动刷新

## Decisions

### D1: 首页职责定为「状态总览」，而不是「任务入口」

- **Decision**：首页呈现系统的**状态数据**（哪些库有问题、知识库摄进去了没有、系统是否就绪），每条都带下一步动作。
- **Why**：这是使用者在设计讨论中的选择。当时摆出的另一条路是「入口卡片墙」（四个能力做成大卡片，点进去就用），被否决——理由是入口在左侧菜单里已经有了，首页再放一遍没有增加信息。
- **被否决方案记录**：入口卡片墙并不差，只是信息密度低。若日后觉得首页「没有可操作的入口」，可以在这套状态总览之上加一条快捷入口带，不必推翻本设计。
- **Trade-off**：**新部署、什么都还没接时，首页几乎是空的**——只有就绪提示与两个空状态引导。这正是 D8 要处理的。

### D2: 两条能力线左右对等，不做主次

- **Decision**：库与知识库各占一栏，结构同构（每个对象一行：名称 + 关键状态 + 下一步动作）。
- **Why**：系统里**只有这两条线有数据沉淀**，它们是对等的。若把知识库压成一行小字（「知识库 3 个 · 文档 45 篇」），首页会看起来像「只管库」的产品，而且**「1 篇文档摄入失败」这类需要处理的状态会被藏起来**——没人会主动去知识库页面翻。
- **Alternatives considered**：单列 + 知识库一行小字（信息更舒展，但上述两点）；只做库、知识库完全不放（更偏）。
- **Trade-off**：内容区变窄，单行信息要更精简（采集时间这类次要信息用小字）。

### D3: 就绪检查只读本地配置，不探测外部服务

- **Decision**：只判断「对话模型 / 嵌入模型各是否有生效配置」，不探测 Qdrant、也不探测模型 API 的可达性。
- **Why**：
  - 读配置是**毫秒级的本地查询**，不会拖慢首页、不会因外部服务无响应而卡住
  - **探测 Qdrant 尤其危险**：客户端的超时取的是 `knowledge_llm_timeout`（默认 **60 秒**）。放进首页请求意味着向量服务一挂，整个首页跟着卡 60 秒——为一个提示把主页面拖死，代价远大于收益
  - 配置缺失是**使用者自己能修**的问题（去「模型配置」加一条），这正是提示要解决的问题；服务不可达则不是，它在实际使用时会以明确错误暴露（知识问答已有的约定：向量服务故障必须与「无命中」区分开）
- **Alternatives considered**：连 Qdrant 一起探、另设 2 秒短超时（能提前发现「配置对但服务挂」，但首页每次加载都多一次外部调用，还要新开健康检查接口）；不做就绪提示、把问题分散到各页面（新部署的人不知道为什么用不了）

### D4: 问题数取「最新快照」，而不是全部快照累计

- **Decision**：每个库的问题分级统计，基于该数据源**最近一次采集快照**的 `catalog_issue`。
- **Why**：同一处问题会在每次采集后重新产出一遍，累加会把「同一个问题」算成多次，数字随采集次数虚增、且不指向任何动作。使用者关心的是「这个库**现在**有多少问题」。
- **配套**：没有快照（未采集 / 采集失败 / 采集中）的库**不显示问题分级**，改显示采集状态 —— 那时「没有问题」与「还没采」是两回事，混在一起会给出误导性的结论（与 SQL 分析侧「没能分析 ≠ 没有问题」是同一条原则）。

### D5: 单个聚合接口，放新模块 `apps/overview/`

- **Decision**：新增 `GET {SYS_NAME}/v1/overview` 一次返回首页全部数据；放在**新模块** `src/apps/overview/`，无数据模型，挂在 `baseviews.StatelessView` 上。
- **Why 单接口**：前端自己拼至少要 5 个请求，其中「每个库的问题数」还是 N+1。首页对延迟敏感，一次取回最省。
- **Why 新模块**：它跨 `datasource` 与 `knowledge` 两个模块聚合，塞进任何一边都会让那个模块承担不属于它的职责。跨模块只读走各模块已声明的服务函数，不直接查其 model（`architecture.md`）。
- **Alternatives considered**：放在某个已有模块（职责不清）；前端并行调多个接口（N+1、加载态难协调）

### D6: 单个模块取数失败不拖垮整个首页

- **Decision**：聚合接口内部对每一块数据**分别兜底**：某一模块查询出错时，该块返回「暂不可用」并记录日志，其余部分照常返回。
- **Why**：首页是入口页，**部分数据取不到时整页报错是最糟的结果**——使用者连能用的部分也看不到了。库里没有问题清单不该导致知识库那一栏也空着。
- **配套**：出错的那块在界面上如实标注，不伪装成「没有数据」（同 D4 的原则）。

### D7: 列表排序：把需要处理的浮上来

- **Decision**：库按「采集失败 / 未采集 → 高危数降序 → 名称」排序；知识库按「有摄入失败 → 有未处理 → 名称」排序。
- **Why**：这个页面的职责是回答「我该关注什么」。按名称排序会让「一个有 5 个高危问题的库」和一堆正常库混在一起，使用者得自己逐个看。
- **Trade-off**：顺序会随状态变化，不固定。对入口页而言这是特性而非缺陷。
- **列表过长时**：列表区域限高并可滚动，不做分页——首页不该有分页控件。

### D8: 空状态给出引导，不留白

- **Decision**：一个库都没接时显示「还没有接入数据库 [去接入]」；没有知识库时同理。
- **Why**：新部署的使用者打开首页看到的就是这个状态（D1 的 Trade-off）。留白等于什么都没说。

### D9: 刷新策略：进入时加载一次 + 手动刷新

- **Decision**：页面挂载时请求一次，另提供一个刷新按钮并显示「最近刷新时间」。**不做轮询、不做自动刷新**。
- **Why**：这些数据变化得很慢（采集是手动触发的），轮询纯属浪费；而使用者刚从采集页回来时，一个刷新按钮就够了。

### D10: SQL 分析不占位置

- **Decision**：首页完全不涉及 SQL 分析——既不展示数据，也不放快捷入口。
- **Why**：它**刻意不落库**（贴一条、看结论、改完就走），没有任何数据可展示。为它单独放一个无数据的入口卡，会破坏「首页 = 状态总览」这个定调。
- **说明**：它是左侧菜单里的一项，点进去就用。若日后觉得需要入口，加一条快捷入口带即可，不影响本设计。

## Risks / Trade-offs

| 风险 | 影响 | 缓解 |
|------|------|------|
| **某模块取数失败拖垮整页** | 首页打不开，连能用的信息也看不到 | 分块兜底（D6）：出错的那块标「暂不可用」，其余照常返回 |
| **库/知识库很多时列表很长** | 首屏被撑长、需要滚动 | 列表限高可滚动（D7）；排序把需要处理的顶上来 |
| **新部署时首页近乎空白** | 使用者以为系统坏了 | 空状态引导（D8）+ 就绪提示（D3）明确告诉他下一步做什么 |
| **问题数被误读为「累计」** | 数字虚高、不指向动作 | 口径写明是「最新快照」（D4），并在界面上标出采集时间 |
| **排序随状态变化** | 使用者找不到刚才那个库 | 库/知识库数量有限；且名称始终展示。列入 Open Questions |
| **无应用层鉴权** | 首页会汇总暴露库名与问题数 | 与基线一致依赖网络隔离；数据本身不含凭据。重申只允许内网部署 |

## Migration Plan

1. 新增模块与路由，无数据表变更、无需 SQL 补丁
2. 前端重写首页（`static/src/views/home/index.vue` 整体替换脚手架内容）
3. 验收：分别在有数据、无数据、混有采集失败三种状态下核对
4. **回滚**：回退代码即可；首页是纯读取，不留任何状态

## Open Questions

1. **排序稳定性**：当前按「需处理程度」排序（D7），状态一变顺序就变。是否需要给使用者一个「按名称排序」的切换？
2. **是否需要「最近活动」**：最近一次采集是何时、最近一条问答是什么。当前只显示每个库的采集时间，没有全局的活动流。
3. **是否给 SQL 分析一个无数据的快捷入口**（D10 选择了不放）。
4. **知识库那栏是否要显示问答会话数**：会话属于问答而非知识库，当前不展示。
