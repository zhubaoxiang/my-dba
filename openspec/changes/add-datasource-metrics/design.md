## Context

前置状态：

- 首页（`add-homepage-overview` 已归档）只展示采集快照里的静态结果：表数、问题分级、采集时间
- 数据源采集是**手动触发**的，快照可能几天前；首页看不出库**现在**的状态
- 已有的只读采集通道：`datasource.services.open_readonly_connection()`（只读会话 + 超时 + 流式游标）
- `jobs/` 目录**已预留但为空**；`start.sh` 里有一行注释掉的 `python /home/src/jobs/cron.py`
- 项目**没有调度机制**：`simple-background-task` 是队列不是调度器，`apscheduler` / `django-q` 均未安装
- gunicorn 跑 **3 个 worker**（`settings/gunicorn.py`），任何随 web 进程启动的周期性任务都会重复执行
- 实测：目标 PG 为 **17.11**（支持 `pg_stat_io`），跑在 Docker 容器里

## Goals / Non-Goals

- **Goals**：让首页反映库**当前**的可用性与负载（在线、连接数、大小、缓存命中），并给出 24 小时趋势，使「这个库最近不对劲」能被一眼看到
- **Non-Goals**：不做机器层面的 CPU / 内存 / 磁盘；不做告警与通知；不做指标的历史范围切换与聚合报表；不引入新的调度依赖或部署容器

## Decisions

### D1: 只采「数据库自己知道」的指标，不碰机器资源

- **Decision**：指标全部通过**已有的只读连接**用 SQL 取得。
- **Alternatives considered**：**读服务器 `/proc`**（`pg_read_file('/proc/meminfo')` 等）。实测**可行**——采集账号是超级用户，能读到内存总量、负载、CPU 累计时间、磁盘 IO。但否决，理由三条：
  1. **需要超级用户**。而数据源采集的定位是「只读采集」，为此把采集账号提权到能读服务器任意文件，权限放得过大
  2. **它本质是「任意文件读」能力**。功能一旦存在，代码里就有读目标服务器本地文件的路径；若日后实现被改成「读使用者指定的路径」，即是文件泄露漏洞。这是本项目引入的第一项此类能力
  3. **强绑 Linux 且 MySQL 走不通**；容器内读到的是宿主机数据，多租户下会越界
- **代价（明确接受）**：首页**没有**机器 CPU / 内存 / 磁盘。
- **磁盘容量须知**：即便走 `/proc` 也拿不到——那里没有文件系统容量，只能执行 `df`。

### D2: 指标落库，由常驻进程周期采集；首页只读本地库

- **Decision**：新增 `datasource_metric` 表；`src/jobs/metrics.py` 常驻采集，每 **5 分钟**一轮；首页从表里读最新值。
- **Alternatives considered**：
  - **首页异步探测**（不落库）：实时且零新机制，但**每次打开首页都要连所有库**，且没有历史、做不了趋势
  - **存进采集快照**：零新调度，但采集是手动触发的，指标可能几天前——对「连接数」这类时效性强的指标几乎无用
- **Why 选它**：首页保持「快、不碰外部服务」的定调；且**有历史才能画趋势**，而趋势正是使用者判断「最近是不是不对劲」的依据。
- **Trade-off**：在线状态最多**陈旧 5 分钟**；间隔内的掉线看不出来。

### D3: 采集进程独立启动并自我守护，避开多 worker

- **Decision**：`start.sh` 里以 `while true; do python jobs/metrics.py; sleep 5; done &` 启动，与 gunicorn 并列。
- **Why**：
  - **独立进程** —— 不随 web 进程启动，gunicorn 三个 worker 各跑一遍的问题天然不存在
  - **外层 `while true` 守护** —— 容器 `restart: always` 只管容器、不管里面单个进程；进程若崩了 5 秒后自动拉起，且**不引入任何新依赖**
  - 循环内**兜住所有异常**，业务出错绝不退出
- **Alternatives considered**：引入 `apscheduler`（新依赖，且仍要解决多 worker 重复）；单独起一个调度容器（部署多一个组件）；系统 cron（容器里没有）
- **局限（写进文档）**：多实例部署时**每个实例都会跑一份**。当前是单实例部署，属已知限制。

### D4: 保留 30 天，每轮顺带清理

- **Decision**：每 5 分钟一轮、保留 30 天 → 每库约 8,640 行；采集轮次结束时删除过期数据。
- **Why**：30 天足够看出「最近一个月有没有变化」，数据量也小。清理放在采集循环里，不再引入第二个定时任务。
- **Alternatives considered**：1 分钟 / 保留 7 天（在线更灵敏，但趋势只能看一周，且对目标库压力更大）；15 分钟 / 保留 90 天（趋势完整，但连接数最多陈旧 15 分钟）

### D5: 趋势图用自绘 SVG，不引图表库

- **Decision**：前端用一个 `polyline` 画火花线（约 30 行），不引入 ECharts 之类的图表库。
- **Why**：项目现在没有图表库；为一条 100×34 的小线引入几百 KB 的依赖不成比例。自绘还能完全控制配色、粗细与渐变，与页面主题一致。
- **配套**：服务端把 24 小时的 288 个点**降采样到最多 48 个**再返回——100px 宽的小图用不着那么多点，传输也更小。

### D6: 趋势的 Y 轴自适应，危险程度用颜色表达

- **Decision**：折线形状**按数据范围自适应**，颜色按**占上限的比例**分档（<80% 蓝、80–95% 黄、>95% 红）。
- **Why**：连接数若固定画到上限（100），9/100 会贴着底部、完全看不出变化；纯自适应又会把 9→10 画得像翻倍。**形状自适应看趋势、颜色报警看危险**，两个目标分开表达。
- **同理应用于数字**：`9/100` 是安全的，`92/100` 该被一眼看到——数字本身加同样的分档着色。

### D7: 知识库卡片铺开，新增三个有信息量的字段

- **Decision**：知识库卡片增加**检索块数**（`chunk_count` 求和）、**文档状态分布条**、**问答次数**（按 `qa_session.knowledge_base_id` 统计），并显示一行描述。
- **Why**：
  - 「32 篇文档」是观感，**「1,204 个检索块」才是实际能检索到多少内容**——上传一篇 200 页 PDF 却只切出 3 个块，光看文档数看不出来
  - 摄入状态天然是**比例关系**，堆叠条比「成功 11、失败 1」的文字更直观
  - 问答次数回答「这个知识库到底有没有人用」——建了 10 个、9 个没人问过是常见情况
- **性能**：三组统计**各一次聚合查询**（`GROUP BY knowledge_base_id`），不逐个知识库查。
- **术语**：界面用「检索块」而非「分块数」——它代表「能被搜到的内容单元」，更贴近使用者理解。

### D8: 页面接受滚动，不为「一屏放下」压缩信息

- **Decision**：首页保持「就绪条 → 概览数字带 → 库卡片网格 → 知识库卡片网格」的纵向结构，**超出即滚动**。
- **Why**：实测 3 个库 + 2 个知识库约 965px，在 1080p 上略超一屏。而库本来就可能接十几个，**「一屏不滚」在多库时必然做不到**；为少数场景把每张卡压到 150px（趋势图缩成小线、看不出形状），等于长期为一个偶发约束付代价。这个页面是**扫视**用的，滚一下很自然。
- **Alternatives considered**：库卡片压缩到 ~150px（能一屏约 800px，但趋势图退化）；改为库 / 知识库左右两栏（约 600px 能一屏，但每栏变窄、指标格变瘦长）

### D9: 新增概览数字带

- **Decision**：页面顶部加一排总览数字：**库数 / 在线数 / 问题合计（含高危数）/ 知识库数与文档数**。
- **Why**：让首屏立刻有内容，也给下面铺开的信息一个总纲。「在线 2/3」这样的比值比单看某个库更早暴露问题。

## Risks / Trade-offs

| 风险 | 影响 | 缓解 |
|------|------|------|
| **采集进程挂掉** | 指标停更，首页显示陈旧值且不易察觉 | 外层 `while true` 守护（崩后 5 秒重启）；循环内兜住所有异常；界面标注「采集于 X 分钟前」让新鲜度可见 |
| **多实例部署时重复采集** | 同一库被采多次、数据重复 | 当前单实例部署；写入文档作为已知限制 |
| **在线状态陈旧** | 间隔内的掉线看不出来 | 界面标明采集时刻；需要实时判断时可直接用「测试连通性」 |
| **指标表持续增长** | 存储累积 | 每轮清理 30 天前的数据（D4） |
| **对目标库的持续连接** | 每 5 分钟一次、24 小时不停 | 只读短连接、用完即关；连接数上限本身也在监控范围内 |
| **MySQL 分支未经验证** | 可能取不到值 | 照 PG 对称实现并标注「未在真实 MySQL 上验证」（与元数据采集器同样的已知限制）；取不到时该库指标留空而非报错 |
| **趋势图误导** | 自适应 Y 轴可能夸大微小波动 | 数字与颜色同屏并列（D6），使用者能对照绝对值判断 |

## Migration Plan

1. 执行 `src/sql/pg_struct.sql`（新库）或 `src/sql/patch.sql`（已有库）：新增 `datasource_metric` 表与索引
2. 部署后端与前端；`start.sh` 已包含采集进程的启动与守护
3. 首次部署后第一轮采集在 5 分钟内完成；在此之前首页显示「指标采集中…」（不留白、不假装）
4. **回滚**：回退代码即可；`datasource_metric` 表可保留（旧代码不读）

## Open Questions

1. **趋势的时间范围切换**：当前只画 24 小时（库里存 30 天）。是否需要 7 天 / 30 天切换？
2. **趋势画哪个指标**：当前固定画连接数（最可操作）。是否需要切换（缓存命中率、库大小）？
3. **是否要告警**：连接数超过阈值、库离线持续 N 分钟时通知。属监控范畴，需先论证边界。
4. **多实例部署时的采集去重**：需要时可用数据库锁或单独的调度容器解决。
