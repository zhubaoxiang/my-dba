## Context

采集阶段已把外键采下来了（`collectors/base.py` 的 `_foreign_keys()`），对外契约 `datasource.services.list_snapshot_tables()` 也把每张表的 `foreign_keys` 暴露出来（含 `columns` 与 `ref_table`）。**但前端没有任何一处用它**——能力在，入口没有。

表详情接口 `catalog/table` 现在返回列 / 索引 / 主键 / 外键 / 体积，其中**只含本表的外键**，没有「谁引用了我」。

## Goals / Non-Goals

- **Goals**：让「这张表跟谁有关」在表详情里一眼看到
- **Non-Goals**：不画图；不做跨数据源；不重复「孤立表」的判定

## Decisions

### D1: 不画图，用列表

- **Decision**：在表详情里给出两段列表（引用了谁 / 被谁引用），可点跳转。
- **Why**：三条理由合起来是决定性的——
  1. **项目一直不引图表库**。首页那条 100×34 的火花线都是自绘的，代码注释写着「为一条 100×34 的小线引入几百 KB 的依赖不成比例」。ER 图要引的图论库比这重得多。
  2. **全库 ER 图在本项目的真实库里不可读**——`ENV_TYPE=local` 那个库 105 张表，画出来是一团线。
  3. **实际要问的是「这张表跟谁有关」**，不是「整个库长什么样」。后者用列表答更快更准。
- **Alternatives considered**：小范围关系图（选中一张表画它与邻居）——仍要绘图能力，且邻居多时手写 SVG 布局会很难看。

### D2: 放在**表详情页**，不新开页面

- **Decision**：作为表详情的一个区。
- **Why**：关系是「这张表」的属性，与列、索引、主键并列。新开一页会让人为了看一张表的关系而丢掉表的上下文。

### D3: 「被引用」必须扫**全库**推导

- **Decision**：由该快照的全部表反查，而不是读本表的定义。
- **Why**：外键是**单向声明**的——`orders.user_id → app_user.id` 只写在 `orders` 上，`app_user` 自身可能一个外键都没有，却被十几张表引用。只读本表会得到「无关系」这个**错误**结论。
- **代价**：每次表详情要遍历快照的全部表。纯内存计算，百来张表可忽略。

### D4: 无关系时明确说明，不留白

- **Decision**：两侧都为空时说明「没有任何外键关系」。
- **Why**：「空」与「还没加载」在界面上长得一样。这与项目一贯的「取不到 ≠ 没有」同一条。

## Risks / Trade-offs

| 风险 | 影响 | 缓解 |
|------|------|------|
| **表详情响应变大** | 表多的库上关系列表可能很长 | 关系通常只有几条；真有热门表被几十张表引用时，列表也仍是可读的（比图好） |
| **引用到快照中不存在的表** | 跳转落空 | 对方表不在本快照时只显示名字、不给跳转 |
| **同名表跨模式** | 定位错表 | 关系里带模式名，与快照里的 `schema + name` 对齐 |
