## Context

`catalog_issue` 的行是**每次采集全量重建**的（`services._save_issues()` 直接 `bulk_create`）。`suggestion` 是文字，`rule_code` 稳定，但**没有任何字段能表达「这一处我不想再看到」**。

首页的问题数由 `datasource.services.list_datasource_status()` 按最近快照统计；问题清单由 `CatalogIssue` 查询。两者是**两条取数路径**——这决定了本变更最需要防的是什么。

## Goals / Non-Goals

- **Goals**：让「我知道的问题」不再重复出现，从而让清单只剩新问题；且**不制造第二套口径**
- **Non-Goals**：不做静音整条规则（已有「停用规则」）；不做批量管理页

## Decisions

### D1: 静音必须是一张**独立的、跨快照**的表

- **Decision**：新表 `issue_mute`，键为 `datasource_id + rule_code + table_name + column_name`（未删除范围内唯一，软删除）。
- **Why**：问题行每次采集重建——把标记加在 `catalog_issue` 上，下次采集就随旧行一起没了。这不是「实现方式」问题，是**数据生命周期**问题。
- **Alternatives considered**：在 `catalog_issue` 加 `is_muted`——看似简单，实际上静音活不过一次采集。

### D2: 粒度是「规则 + 表 + 列」

- **Decision**：精确到某张表的某个列上的某条规则。
- **Why**：比它粗的「规则 + 表」会把后来新增的同类真问题一并静默掉；比它更粗的「整条规则」就是现成的「停用规则」，没必要再做一遍。**静音的价值就在于精确**。
- **Alternatives considered**：同时支持表级与列级——多一层选择，且表级容易误伤，先看实际用不用得上。

### D3: 静音**全局生效**，不是「只在清单里隐藏」

- **Decision**：被静音的问题在问题清单与**各处的问题统计**（首页问题合计、库卡片的分级问题数）中都不再计入。
- **Why**：这是本变更最容易做错的地方。只在清单里隐藏、首页照算，会立刻造出「首页说 7 条、清单只有 5 条」——**两处口径打架**，而这个项目一路都在躲的就是这个（首页的规则条数与清单页、`取不到 ≠ 没有`）。
- **代价（明确接受）**：静音会让首页数字**变小**。这是它的本意（「别再当它是待办」），但必须让使用者知道——界面上要说明「静音后该处不再计入统计」。
- **实现要求**：问题清单与问题统计的过滤**走同一个函数**，不允许两处各写一遍——口径分叉往往就是这么来的。

### D4: 与「停用规则」在界面上讲清区别

- **Decision**：静音时明确说明「只影响这一处」，并指出「停用规则是全局的」。
- **Why**：两者都能让问题消失，但影响面差了一个数量级。混了之后，使用者想静音一处结果关掉了一整条规则。

## Risks / Trade-offs

| 风险 | 影响 | 缓解 |
|------|------|------|
| **静音后忘掉，问题被永久掩盖** | 真实问题不再有人看 | 顶部常驻「已静音 N 条」与查看入口；查看页可取消 |
| **清单与统计口径分叉** | 数字对不上 | D3：两处走同一函数；补单测直接断言两者一致 |
| **静音键与问题行的匹配漂移** | 重新采集后静音失效 | 键取的都是稳定值（`rule_code` 稳定、表/列名来自库），不取 `target` 这类拼接串 |
| **把静音当成「已修复」** | 事实上没修，只是不报了 | 界面措辞用「静音」而不是「已处理/已修复」——**它不表示问题消失了** |

## Migration Plan

新建表 `issue_mute`：DDL 追加到 `sql/pg_struct.sql` 与 `sql/patch.sql`。

因为是**新表**，旧代码不引用它、新代码需要它，故**代码与补丁需同时上线**（新代码会查这张表）。表结构变更本身不影响既有数据。
