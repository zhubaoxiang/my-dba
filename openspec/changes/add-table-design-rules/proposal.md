# Change: 库表规则补上「表设计」这一层

## Why

现有 7 条规则覆盖的是**运维/健康**层面——主键有没有、索引够不够、表是不是太大、有没有孤立。**表设计**层面只有「可疑字段类型」一条（用字符存时间 / 超长 varchar / 大对象）。

而使用者的画像是**开发与测试人员**，他们最常问的恰恰是设计层面的问题：「这个字段类型选得对吗」「这张表是不是该拆」「删掉这条记录会带走什么」。

README 把「看懂库表结构与隐患」列为第一个诉求，现在只做到了「隐患」，缺了「设计」。

## What Changes

新增 5 条规则。前 4 条只用快照里**已有**的数据；第 5 条需要先补一处采集。

| 规则 | 级别 | 判据 | 修复语句 |
|------|------|------|---------|
| **金额类字段使用浮点类型** | 高 | 类型是浮点 **且** 列名或注释含金额语义 | 模板：`ALTER COLUMN … TYPE numeric(19,4)` + 前提 |
| **主键使用长字符类型** | 中 | 主键列是字符类型，长度无界或超阈值（默认 64） | 需模型参考（改主键涉及数据迁移） |
| **宽表（列数超阈值）** | 中 | 列数超阈值（默认 50） | 需模型参考（拆表要业务判断） |
| **索引体积超过数据体积** | 中 | 索引占用 > 数据占用，且表有数据 | 不给出语句，指向逐索引的那两条 |
| **跨表的级联删除链** | 中 | 本表的 `ON DELETE CASCADE` 指向的表**自己也有** CASCADE 出边 | 需模型参考（改不改是业务决定） |

**采集扩展**：外键关联补上**删除与更新动作**（PG 的 `pg_constraint.confdeltype`、MySQL 的 `REFERENTIAL_CONSTRAINTS.DELETE_RULE`）。现在的采集器只取外键的列与目标表——不取动作，**级联删除就藏得看不见**。

两条新阈值（`primary_key_max_length` / `wide_table_max_columns`）走既有的规则注册表机制，可运行时调整。

## Impact

- 受影响能力：**修改** `metadata-catalog` 的**两条**需求——
  - 「元数据采集范围」：外键关联补「删除与更新动作」
  - 「库表健康问题分析」：规则枚举补 5 条
- 受影响代码：
  - `src/apps/datasource/collectors/`（两处方言：外键补动作）
  - `src/apps/datasource/rules/definitions.py`（5 条规则 + 常量）
  - `src/apps/datasource/fixes.py`（金额那条的模板；其余归「需模型参考」与「不给语句」）
  - `docs/datasource.md`（规则清单表、采集范围、明确不做的）
- 无新依赖、无 DDL、无部署形态变化
- **既有数据源需要重新采集**才会产出第 5 条规则的问题（外键动作是这次才补采的）；前 4 条同样需要重新采集，因为 `catalog_issue` 每次采集重算

## 明确不做

- **不做命名规范规则**（表名/列名必须 snake_case）：那是**本项目代码**的规范，不该强加给被管理库
- **不做注释覆盖率、可空列占比**：噪音大，与「清单里全是噪音就再也不看了」直接冲突
- **不做「表必须有 created_at / updated_at」**：那是本团队的约定，不是通用问题。真要做得做成默认关闭的可选规则，另案
- **不报单层级联与自引用级联**：前者是声明者的本意，后者（`parent_id → 本表`）是树形结构的常规做法——见 design.md D6
