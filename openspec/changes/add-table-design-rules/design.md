## Context

现有 7 条规则：`no_primary_key` / `fk_without_index` / `duplicate_index` / `unused_index` / `big_table` / `suspicious_column_type` / `isolated_table`。

采集器能给的字段（决定了「什么判得了」）：

- 表：`schema` / `name` / `comment` / `row_count` / `data_size` / `index_size` / `total_size`
- 列：`name` / `ordinal` / `data_type` / `length`（无界为 -1）/ `nullable` / `default` / `comment`
- 索引：`name` / `unique` / `primary` / `index_type` / `columns` / `scans`
- 主键：`name` / `columns`；外键：`name` / `columns` / `ref_schema` / `ref_table` / `ref_columns`
- 外键的**删除/更新动作**：本次**补采**才有的（PG 的 `pg_constraint.confdeltype` / MySQL 的 `REFERENTIAL_CONSTRAINTS.DELETE_RULE`）

**筛选标准**（按重要性排序）：有价值 × 判得了 × **误报低**。第三项是这个项目的硬约束——「清单里全是噪音，就再也不看了」。

## Goals / Non-Goals

- **Goals**：把规则从「运维健康」扩到「表设计」；新增的每条都要能说清误报边界
- **Non-Goals**：不做命名规范、注释覆盖率、可空列占比（见 proposal 的「明确不做」）

## Decisions

### D1: 金额字段用浮点——**判据收窄到「类型是浮点 + 名字/注释说是钱」**

- **Decision**：`data_type` 属浮点族（`real` / `double precision` / `float` / `double` / `float4` / `float8`）**且**列名或注释匹配金额语义（`amount` / `price` / `fee` / `cost` / `balance` / `金额` / `价格` / `费用` / `余额`）。
- **Why**：浮点存金额会丢精度（`0.1 + 0.2 ≠ 0.3`），而且**越晚改越贵**——已有数据要迁移，丢掉的精度还找不回来。这是经典且严重的建模错误。
- **为什么不报所有浮点列**：浮点在科学计算、统计指标里是**正确选择**。一律报会立刻把这条规则变成噪音源。
- **代价（明确接受）**：**会漏报**——列名叫 `total` 又没注释就判不出来。这个方向的取舍是刻意的：**漏报比误报便宜**。
- **级别「高」**：它属于「已经错了、且越拖越贵」那一类，与 `no_primary_key` 同级。

### D2: 主键用长字符——阈值可配，且**不产出模板语句**

- **Decision**：主键列属字符类型且（长度无界 或 长度 > `primary_key_max_length`，默认 64）。归到**需模型参考**，不给模板语句。
- **Why**：主键会被**所有**引用它的外键与索引各复制一份——`varchar(255)` 的主键让每张引用表每行多背 255 字节。阈值取 64 是因为短业务键（订单号、编码）通常在这个量级以内。
- **为什么不给模板**：「改主键」要么加代理键、要么缩短现有列，两条路都涉及**数据迁移**，没有唯一答案——与「超大表」同类。
- **误报边界**：无界（`length == -1`）在 PostgreSQL 上对应 `text` 类型主键，是明确的问题；有界但超过 64 的要看业务（UUID 存成 `char(36)` 算边界情况，64 以内不报）。

### D3: 宽表——阈值默认 50，级别「中」

- **Decision**：`len(columns) > wide_table_max_columns`（默认 50）。归到**需模型参考**。
- **Why**：列数过多意味着建模没拆开，`SELECT *` 与整行读写都会变重。
- **为什么默认 50**：业务表 30~40 列很常见，定在 30 会刷屏；PostgreSQL 的硬上限是 1600，定在 100 又太晚。50 是「明显该看一眼」的量级，且可运行时调整。
- **误报边界**：宽表本身是设计味道不是错误。级别「中」而非「高」就体现了这一点。

### D4: 索引体积超过数据——**整表视角**，与逐索引的两条互补

- **Decision**：`index_size > data_size` 且 `row_count > 0` 且**数据占用达到最小体量**（`index_overweight_min_data_mb`，默认 100）。**不给出语句**，在建议里指向「重复或冗余索引」与「疑似未使用索引」。
- **Why**：现有的两条索引规则都是**逐索引**看的（这个重复了、这个没用过），缺一个**整表**视角：索引加起来比数据还大，说明要么索引太多、要么索引太宽。它本身不是可执行的动作，而是一个「该去看那两条了」的信号。
- **为什么要求 `row_count > 0`**：空表的数据占用接近 0，索引稍大就会触发——那不是问题，是空表的正常形态。
- **为什么加了体量下限（**6.4 真机核对逼出来的**）**：初版判据只比大小，第一次在真实库上跑出来 **6 条全是误报**——`data=8192` 字节、1~42 行的表，措辞还显示成「索引占用 0 MB，超过数据本身的 0 MB」。**小表的 `index > data` 是必然形态**（索引有固定的页开销），比值没有意义。这一条与 D1（不报所有浮点列）、D6（不报单层级联）是同一类修正：**判据要卡在「这件事真的值得看一眼」的体量上**，而不是只要条件成立就报。
- **为什么走 `advisory` 而不是 `model_required`**：这里的修复动作**不是没有唯一答案，而是取决于逐索引判断**——而那个判断已经有两条规则在做，且它们能给出具体语句。让模型再猜一遍只会重复。

### D5: 「单表索引数超阈值」不做

- **Decision**：本次不做，只做 D4。
- **Why**：与 D4 高度重叠。体积是**结果**（索引多、索引宽、列类型大都会反映在体积上），条数是**原因之一**。两条都做会让同一张表报出两条几乎同义的问题。体积更本质。
- **若将来仍要**：它应该定「低」级别，并明确与 D4 的关系（是 D4 的细分还是独立信号）。

### D6: 级联删除——只报**跨表的链**，不报级联本身

- **Decision**：报的条件是「本表的 `ON DELETE CASCADE` 指向的表**自己也有** CASCADE 出边」——即删除会**跨两层以上**传递下去。
- **为什么不能报所有 CASCADE**：`ON DELETE CASCADE` 本身是**合法且常用**的设计（订单项随订单删）。一律报会立刻把这条规则变成噪音源——与 D1 里「不报所有浮点列」是同一条思路。
- **为什么不报自引用级联**：`parent_id → 本表` 的 CASCADE 是**树形结构的常规做法**（部门树、评论树），删父节点带走子节点正是声明者的本意。
- **为什么不报单层级联**：同上——A 删带走 B，这是 `CASCADE` 这个词的字面意思，没有意外。
- **剩下那一种才是真意外**：A 删带走 B，而 **B 又带走 C**——多层传递会带走使用者根本没意识到的东西，而且**不翻约束定义看不出来**。
- **代价（明确接受）**：真正想让人知道的「本库有 N 条级联删除」这件事，这条规则**不会**说。它只挑出最危险的那一类。若将来想让使用者看到全貌，那更适合做成库概览里的一条**信息**（不是问题），另案。
- **需要补采**：动作字段现在没采，判不出来。
- **归到「需模型参考」**：改成 `RESTRICT` 的语句是确定的，但**要不要改是业务决定**——与「主键用长字符」「宽表」同类。

## Risks / Trade-offs

| 风险 | 影响 | 缓解 |
|------|------|------|
| **D1 漏报** | 列名/注释不含金额语义的浮点列判不出 | 明确接受（D1）；漏报不比误报糟 |
| **D3 阈值偏高** | 50 列以下的宽表不报 | 可运行时调整；调低了会刷屏，使用者自己权衡 |
| **新规则让问题数明显上升** | 使用者第一次看到一堆新问题 | 级别分档（高/中）；不满意的可以**逐条静音**（`add-issue-mute`）或停用整条规则 |
| **D4 与另两条索引规则同时命中** | 同一张表报三条关于索引的问题 | 三类问题**定位不同**（整表体积 / 具体索引重复 / 具体索引未使用），不是同义重复；但若实测发现吵，可把 D4 降为「低」 |
| **D6 判据太窄，等于没报** | 跨表级联链在某些库里确实少见 | 明确接受——它的价值不在覆盖率，而在**挑出那一种不翻约束就看不见的传递删除**。想让人看到级联全貌，那是库概览的信息，不是问题 |
| **补采外键动作后，旧快照判不出 D6** | 重新采集前该规则不产出 | 既有机制的常态（`catalog_issue` 每次采集重算）；文档里写明需要重新采集 |

## Migration Plan

无数据与部署变更：只加规则，规则清单与阈值走既有的注册表机制。

**既有数据源需要重新采集**才会产出新规则的问题——`catalog_issue` 是每次采集重算的。不重采则新规则对历史快照不生效，这是既有机制的常态，不是本次引入的。
