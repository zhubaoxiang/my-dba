## Context

库表分析的产出是 `catalog_issue` 行，每行已有 `description`（问题说明）与 `suggestion`（一句文字建议）。规则在判出问题时**手里有完整对象**（表、列、索引），但只有文字被存下来。

7 条规则共 9 个判定分支，逐个看过：

| 分支 | 能否给出确定语句 |
|------|----------------|
| 外键缺索引 / 重复索引 / 冗余索引 / 未使用索引 / 孤立表 / 超长 varchar / 字符存时间 | ✅ 对象全在手 |
| 无主键表 | ✅ 能（建议文字本就写了「增加自增代理主键」），但要带「若无业务唯一列」的前提 |
| 超大表（分区/归档） / 大对象拆表 | ❌ 无唯一答案——要选分区键、定拆分策略 |

与既有基调的关系：只生成不执行（同 `nl2sql`）；判定与生成都走确定性代码，不交给模型。

## Goals / Non-Goals

- **Goals**：把「发现了问题」变成「拿到可用的语句」；**让使用者能分辨哪条是算出来的、哪条是建议的**
- **Non-Goals**：不执行；不替使用者判断该不该修；不给模板能覆盖的分支引入模型

## Decisions

### D1: 模板为主，模型只补那两条没有唯一答案的

- **Decision**：对象确定的分支走确定性模板；超大表与大对象拆表交模型。
- **Why**：对象名已经在规则手里，模板能拼出**确定**语句且可单测、零幻觉、不依赖模型可用性。只有「没有唯一答案」的两条才需要判断，而那里模型的输出也只是**一种**建议。
- **代价（明确接受）**：模板只覆盖 7/9 个分支，剩下 2 个的质量取决于模型。

### D2: 两类**分区陈列、各自标明来源**

- **Decision**：模板生成的与模型生成的在界面上分两块陈列，分别标注「由规则对象直接得出」与「无唯一答案，仅供参考」，后者还必须写明前提（如「按 created_at 做月度分区」）。
- **Why**：这是 D1 的**必要配套**。模板语句是**算出来的**，模型语句是**一种建议**——两者混在一起展示，使用者会同等信任。这正是这个项目反复守的线（`取不到 ≠ 没有`、`校验通过 ≠ 语义正确`）。把来源与前提写在脸上，是把「不确定」如实交出去的唯一办法。
- **Alternatives considered**：模型那部分只给思路不给语句——避免被当成确定答案，但那些恰恰是最难的问题，不给语句等于又回到「发现问题然后就没下文」。

### D3: 存**原料**，不存**成品**

- **Decision**：`catalog_issue` 新增 `object_name`（索引名），而**不是** `fix_sql`（语句本身）。语句在读取时按当前模板算。
- **Why**：语句是**派生物**。存成 `fix_sql` 就等于把模板当时的输出固化进库——模板一改（比如索引名要加 schema 前缀），历史快照里的语句便是旧的，而使用者分不出哪些是旧的。这与本项目刚吃过的那次教训同源：**别存会过期的副本**。
- **代价**：读取时多一次纯计算。7 条规则、百来张表，可忽略。
- **为什么必须加这一列**：索引类规则的 issue 里，`column_name` 存的是**列名列表**，索引名**只出现在描述文字里**。不改数据结构，`DROP INDEX xxx` 就只能靠解析中文描述得出——那是脆的。

### D4: 模板随清单一并返回，模型按需

- **Decision**：问题清单接口直接带上模板语句；「需你决策」的两条给一个按钮，点了才调模型。
- **Why**：模板是纯计算，零延迟零成本，藏到按钮后面等于默认看不到——而它是这个功能的主产出。模型有延迟与成本，且只在少数问题上用得上，按需才合理。

### D5: 每条语句带风险前提，且绝不执行

- **Decision**：删除类语句标「确认无其他依赖后」，类型变更类标「数据不合法时会失败」；**任何情况下都不执行**。
- **Why**：`DROP INDEX` 可能被别的约束依赖，`ALTER COLUMN TYPE` 在有脏数据时直接失败。给一条语句而不给它的前提，等于把人往坑里推。不执行则与 README 的边界一致。

## Risks / Trade-offs

| 风险 | 影响 | 缓解 |
|------|------|------|
| **模型那两条给错语句** | 使用者照做会出问题 | D2 的显式标注与前提；两条都属「本来就需要人来决策」的形态 |
| **模板语句被当作「官方答案」** | 不看前提就执行 | 每条都带前提；语句区标「先在测试库验证」 |
| **`object_name` 只对部分规则有值** | 读取时要判空 | 模板生成在前置判断里处理；无对象名的问题自然落到「走模型/不给语句」 |
| **一次性给出整库修复语句，被整段执行** | 大面积变更 | 不提供「一键执行」；复制是唯一的出口动作 |

## Migration Plan

`catalog_issue` 新增 `object_name varchar(256) NOT NULL DEFAULT ''`——**加列且带默认值**，因此新代码 + 旧表结构也能跑（读取到的为空串）。但新代码会 SELECT 该列，故：

**代码与补丁仍需同时上线**，顺序无所谓（加带默认值的列不像删列那样会双向打架）。补丁追加到 `sql/patch.sql`，并同步 `sql/pg_struct.sql`。历史问题行的 `object_name` 为空 → 那几条老问题暂时给不出索引类语句，重新采集后即正常。
