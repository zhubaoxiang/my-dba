## MODIFIED Requirements

### Requirement: 规则管理接口

系统 SHALL 提供规则清单查询与管理接口：规则清单 MUST 以**代码声明为基底**、叠加库中已存的覆盖项后返回，使从未落库的规则也出现在清单中并展示代码默认值；MUST 支持修改启用状态、修改级别、修改阈值、恢复默认。规则 MUST 以其 `code` 定位，MUST NOT 依赖数据库自增主键。列表查询 MUST 分页。

#### Scenario: 查询规则清单（含尚未落库的规则）

- **WHEN** 请求规则清单，且某条规则在库中没有任何记录
- **THEN** 该规则 MUST 出现在清单中，其级别、启用状态与阈值取自代码声明

#### Scenario: 清单反映人工调整

- **WHEN** 某条规则的级别已被人工调整后请求规则清单
- **THEN** 该规则展示调整后的值，并标明该规则已被调整

#### Scenario: 修改启用状态

- **WHEN** 请求停用某条规则
- **THEN** 该规则记录被更新为停用状态，接口返回成功

#### Scenario: 修改为非法级别

- **WHEN** 请求把某条规则的级别设为不存在的档位
- **THEN** 系统返回参数错误（code 4000），规则不被修改

#### Scenario: 修改阈值格式非法

- **WHEN** 请求提交的阈值不是合法的键值结构
- **THEN** 系统返回参数错误（code 4000），规则不被修改

#### Scenario: 使用不存在的规则代码

- **WHEN** 请求操作一个不在代码声明中的规则 `code`
- **THEN** 系统返回资源不存在（code 4004）

### Requirement: 规则管理界面

系统 SHALL 提供前端页面用于查看与调整规则，页面 MUST 在同一处呈现**库表分析规则**与 **SQL 分析规则**两组清单，并显示各自的规则条数。库表规则组 MUST 提供启用开关、级别调整与阈值编辑入口；SQL 规则组 MUST 只读展示。一组内不具备的能力 MUST NOT 以禁用（置灰）控件伪装。

#### Scenario: 两组规则同页可见

- **WHEN** 用户进入规则页面
- **THEN** 页面同时提供库表分析规则与 SQL 分析规则的清单，并显示各自的规则条数

#### Scenario: 库表规则可调整

- **WHEN** 用户在库表规则组中停用某条规则
- **THEN** 页面反映该规则已停用，后续分析不再产出该规则的问题

#### Scenario: SQL 规则只读

- **WHEN** 用户查看 SQL 规则组
- **THEN** 该组展示标识、名称、级别与是否需要表结构，MUST NOT 出现启用开关或级别调整控件

## ADDED Requirements

### Requirement: 规则恢复默认

系统 SHALL 提供将单条规则的可覆盖项恢复为代码默认值的能力。系统 MUST NOT 要求任何「同步」动作作为查看或调整规则的前置条件。

#### Scenario: 恢复默认

- **WHEN** 对某条已人工修改的规则执行恢复默认
- **THEN** 该规则的启用开关、级别与阈值回到代码声明的默认值

#### Scenario: 未落库的规则无可恢复项

- **WHEN** 对一条从未被修改过（库中无记录）的规则执行恢复默认
- **THEN** 系统返回参数错误，且 MUST NOT 产生任何数据库记录

#### Scenario: 无需同步即可查看全部规则

- **WHEN** 查看规则清单，且从未执行过任何同步动作
- **THEN** 清单 MUST 展示全部规则及其代码默认值

## REMOVED Requirements

### Requirement: 规则同步与恢复默认

**Reason**: 清单改为「代码声明为基底 ⊕ 库中覆盖」后，「同步」不再是查看规则的前置动作——页面不再依赖库中有行才能显示规则。第一次修改某条规则时由该次修改自动落库。其中「恢复默认」的能力仍然需要，已在 `### Requirement: 规则恢复默认` 中重新定义。

**Migration**: 移除 `POST {SYS_NAME}/v1/analysis-rule/sync`。使用者不需要任何替代动作：不调用它也能看到并调整全部规则。已落库的覆盖项与既有 `analysis_rule` 行不受影响，无需数据迁移。
