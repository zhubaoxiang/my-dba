## Context

规则在两处存在，但真值只有一处：

- **代码声明**是规则默认值的唯一来源（`apps/datasource/rules/definitions.py` 7 条、`apps/sqlanalysis/rules/definitions.py` 18 条）
- **`analysis_rule` 表**只存**覆盖项**（启用开级、严重级别、阈值），且**只有点过「同步规则」才有行**

规则清单页读的是后者，于是全新部署下页面为空，而首页显示 7 条（首页按 D3 取自代码声明）。

两条能力线的规则可做的事也不同：库表规则**可调**（有覆盖机制），SQL 规则**没有覆盖机制**，只能看。

## Goals / Non-Goals

- **Goals**：规则清单一打开就有内容；两类规则在同一页看到；首页两格对称
- **Non-Goals**：不做自定义规则（DSL）；不做试运行；不改判定逻辑；不迁移内置规则进库

## Decisions

### D1: 清单以「代码声明为基底 ⊕ 库中的覆盖」返回

- **Decision**：`list()` 遍历 `registry.all_rules()`，每条去 `analysis_rule` 找同 `code` 的行；找到则用行里的 `enabled` / `level` / `thresholds` 覆盖，找不到则用代码默认值并标 `id: null`。
- **Why**：这才是「库中无记录时分析使用代码声明的默认值」这条既有约定的**页面侧对偶**——分析早就这么做了。让页面与分析的取数口径一致，是消灭「首页 7 条、清单 0 条」这个矛盾的唯一办法。
- **代价**：清单接口不再是一次单纯的 ORM 查询，而是一次「声明 × 覆盖」的合成。规则只有 25 条，代价可忽略。
- **Alternatives considered**：
  - **进页面自动同步一次**（GET 触发写库）：页面改动最小，但 GET 产生写操作与 HTTP 语义相背；本仓库接口无应用层鉴权，GET 触发写入风险更大。
  - **只加空状态引导**（「请点同步」）：把「同步」这个内部机制暴露给使用者，且 SQL 规则仍不在这页。

### D2: 规则定位从 `id` 换成 `code`（BREAKING）

- **Decision**：`PUT/PATCH {SYS_NAME}/v1/analysis-rule/{code}`、`POST {SYS_NAME}/v1/analysis-rule/{code}/reset`。
- **Why**：D1 之后，未落库的规则**没有自增 id**，却必须可被修改。`code` 是规则本来就有的稳定标识（`analysis_rule` 上有 `uk_analysis_rule_code` 唯一索引），用它定位既解决「没有 id」，也让接口语义与「规则」这个实体对齐。
- **代价**：接口破坏性变更。本仓库接口只被本前端消费，无外部调用方，一起改即可。
- **Alternatives considered**：保留 `{id}` 并另开一个按 code 操作的端点——两套定位方式并存，读代码的人得先判断该用哪个。

### D3: 移除「同步规则」，改为「修改时自动建行」

- **Decision**：`sync` action 删除。`update` 在库中无该 `code` 时**自动建立记录**再保存覆盖值。
- **Why**：D1 之后「让页面有数据」不再是同步的职责，它只剩「批量预置库行」——而那是**使用者不该操心的内部机制**。第一次调整某条规则时顺手建行，使用者永远不需要知道有张表。
- **代价**：修改操作会写库。这是 `PUT` 的语义本身，不是隐式副作用；`GET` 仍然不写库。
- **Alternatives considered**：保留按钮并改名为「写入默认值」——行为显式，但会让使用者以为「不点就没生效」，反而制造疑问。

### D4: 两个 Tab，各调各的端点，不造第三个「统一规则」接口

- **Decision**：库表 Tab 调 `{SYS_NAME}/v1/analysis-rule`，SQL Tab 调 `{SYS_NAME}/v1/sql-analysis/rules`。
- **Why**：一个「统一规则」接口既不属于 `datasource` 也不属于 `sqlanalysis`，会成为第三个真相源，与 `architecture.md` 的「跨模块只读走对方模块的服务函数」冲突。两半的可做的事本就不同（一半可调、一半只读），各取各的反而更诚实。
- **Alternatives considered**：一个接口返回两组——前端少一次请求，代价是凭空造出一个没有归属的模块。

### D5: SQL 规则 Tab 只读，不给置灰控件

- **Decision**：SQL 规则表只列四列（标识 / 名称 / 级别 / 是否需要表结构），**不出现**启用开关与级别下拉。
- **Why**：SQL 规则没有覆盖机制，给了控件也点不动。置灰控件是在暗示「本来可以，只是现在不行」——比没有控件更误导。
- **这一不对称是现状**：要消除它得先给 SQL 规则做覆盖机制，超出本变更范围。

### D6: 库中的「孤儿行」不展示，也不主动删除

- **Decision**：`analysis_rule` 里存在但已不在代码声明中的 `code`（历史上规则被删过），不出现在清单里；也不清理。
- **Why**：D1 之后清单的基底是代码声明，不在声明里的自然不在清单里。删除是不可逆操作，而这些行不占用任何东西、也不影响分析（`load_effective_rules` 只遍历声明）。
- **Alternatives considered**：清理孤儿行——让库更干净，但把一个无害的冗余变成一次有风险的数据删除。

## Risks / Trade-offs

| 风险 | 影响 | 缓解 |
|------|------|------|
| **`{id}` → `{code}` 漏改调用点** | 规则调整功能整体失效 | 全仓库只有 `rules.vue` 一处消费者；改完做一次真实接口核对 |
| **「改时自动建行」引入写操作** | 有人担心「看一眼就写了」 | 写入只由 `PUT/PATCH` 触发，`GET` 不写库；`reset` 对未调整过的规则直接返回 400，前端也置灰该按钮 |
| **两个 Tab 的数据口径不同**（一个含覆盖、一个是纯声明） | 有人以为 SQL 规则也能调 | SQL Tab 表头写明「只读」；标签上带条数，与首页的两个数对得上 |
| **SQL 规则清单与首页计数是两条取数路径** | 一处改了另一处没改 | 两处都取自 `sqlanalysis/rules/registry.all_rules()`，同一来源 |

## Migration Plan

无数据与部署变更。回滚即回退代码。

`analysis_rule` 表结构不变，新增的写入路径（upsert）与既有行兼容。
