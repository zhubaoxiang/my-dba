## Context

前置状态：

- 首页（`add-homepage-overview` 已归档）的结构是：就绪条 → 概览数字带 → 库卡片网格 → 知识库卡片网格 → 页脚
- 系统里有**两套规则注册表**，来源、主语、覆盖机制都不同：
  - `apps/datasource/rules/`：**库表分析规则 7 条**（6 条表级 + 1 条列级），主语是库表对象；可在 `/datasource/rules` 页调整启用、级别、阈值（落在 `analysis_rule` 表）
  - `apps/sqlanalysis/rules/`：**SQL 分析规则 18 条**，主语是语句；**没有清单页，也没有覆盖机制**
- 两者的关系已有定论但未实施：`apps/sqlanalysis/rules/registry.py` 的 docstring 写明「将来接入统一规则注册表时，由 scope 维度区分这两类规则」
- 首页的既有约定：单个接口一次取回、逐块兜底、取不到不伪装成 0

## Goals / Non-Goals

- **Goals**：让「系统在替使用者检查什么」在首页可见；给库表规则清单一个入口
- **Non-Goals**：不做统一规则注册表；不给 SQL 规则做清单页；不做启用/关闭状态展示；不做规则条数的历史变化

## Decisions

### D1: 只给条目数，不给启用状态

- **Decision**：两块各显示一个数——库表规则 7 条、SQL 规则 18 条。
- **Alternatives considered**：连启用数一起给（「7 条中启用 6」）。
- **Why**：**启用状态的价值不在首页，而在问题数旁边**。「关掉几条规则后，0 个问题意味着什么」是问题数的限定条件，贴在问题数上是限定，单独摆一个数是摆设。后端已有 `evaluated_rule_count` / `enabled_rule_count` 可用，需要时在库卡片页脚加即可，属另一个位置的决定。本次诉求就是条目数，多做会把这块从「规模」变成「配置快照」。

### D2: 拆成概览数字带的第 4、5 两格

- **Decision**：分析规则**不单独成块**，而是作为概览数字带的**两格**（库·在线 / 问题合计 / 知识库 / 库表规则 / SQL 规则），每格一个大数字配自己的标签。
- **Why**：数字带承担的是「**整个系统的规模一览**」——库多少、问题多少、知识库多少、系统在替你看多少条规则。放在一排里一眼扫完，比散落到页尾更好找。
- **为什么不挤在一格**（本次修订）：初版把两个数并进第 4 格，用 `·` 分隔、标签写成「分析规则 · 库表 / SQL」。实际效果是**两个数被读成一个怪数字**（`7·18`），标签也密到不像标签——诉求「让系统的判断标准可见」没达成，反而更糊。拆成两格后每个数都有 26px 大字和独立标签，才真正看得见。
- **代价（明确接受）**：五格里有两格是不随状态变化的静态数，稀释「有问题要处理」的紧迫感。数字带的口径因此是「规模一览」而非「待关注的规模」——这是这两格带来的变化，不是措辞问题。
- **Alternatives considered**：
  - **两个数挤在第 4 格**（初版实现，提交 46bf304）：省一格，但两个数被读成一个、标签过密，就是本次要修的问题。
  - **单独一块放在页尾**（提案初稿的选择）：口径更干净（那一带全是随状态变的东西），但规则条数要滚到最底下才看得到，等于没有。
  - **与库卡片左右分栏**：库卡片区已经是两列网格，再挤一栏会让卡片变窄。
- **配套**：库表规则那格带「查看规则清单」入口（D5），SQL 规则那格不带——它没有清单页可去。

### D3: 条目数取自代码声明，不取库里的行数

- **Decision**：两处 `rule_counts()` 都返回 `rules.registry.all_rules()` 的长度。
- **Why**：库表规则的 `analysis_rule` 表**只有同步过之后才有行**。数库里的行数会在「还没点过同步」时得到 0——而那时规则其实有 7 条、分析也照常跑（代码声明是全集与默认值来源，库是覆盖层）。**数出 0 是把「没同步」说成了「没有规则」**。
- **Trade-off**：条数反映的是**代码里有什么**，不是**库里配成什么**。这正是 D1 要的那个「规模」口径。

### D4: 跨模块走各自模块的服务函数，不直接 import 对方的注册表

- **Decision**：新增 `apps/sqlanalysis/services.py` 提供 `rule_counts()`；`apps/datasource/services.py` 同形再提供一份；`overview` 只做聚合。
- **Why**：`architecture.md` 规定跨模块只读要走对方模块的服务函数，不直接查其内部。注册表虽然是只读的，但它属于模块内部结构——直接 import 会让「SQL 规则从哪来」这件事在 overview 里长出第二处真相。
- **代价**：为一个三行的函数新开一个 `services.py`。可接受：`apps/sqlanalysis/` 目前确实没有服务层，而它已经有 6 个内部模块，服务层早晚要有。
- **Alternatives considered**：让 `overview` 直接调两个注册表——省一个文件，但破坏分层约定。

### D5: SQL 规则那格没有入口

- **Decision**：库表规则那格链到 `/datasource/rules`；SQL 规则那格只给数，不给链接。
- **Why**：SQL 规则**没有清单页可去**（见 Context）。做一个链接指向不存在的地方更糟。
- **这一不对称属于现状**，写进 `docs/overview.md`。要消除它，要么给 SQL 规则也做清单页，要么落 D 里的统一注册表——都超出本变更范围。

## Risks / Trade-offs

| 风险 | 影响 | 缓解 |
|------|------|------|
| **静态数字，长期不变** | 使用者看过一次就不再是信息 | 它是「规模锚点」而非状态；带上「查看规则清单」入口，需要细节时能走下去 |
| **数字带口径被稀释** | 四格里有一格不随状态变化，「待关注」的指向变模糊 | 明确接受（D2）；数字带改口径为「规模一览」，不再声称每一个数都是待办 |
| **两块取数失败表现不一致** | 一个数有一格没有，看起来像「另一方规则为 0」 | 两块各自 `None` 并显示占位符，**不显示 0**；与既有「取不到不伪装成没有数据」同一条原则 |
| **条数口径被误读为「已启用数」** | 有人看到 7 会以为 7 条都在跑 | 文案用「条目数」；启用数按 D1 不在此处展示 |

## Migration Plan

无数据与部署变更：纯展示层与只读契约。回滚即回退代码。

## Open Questions

1. **SQL 规则要不要清单页**：现在 18 条规则在界面上列不出来，只能看到数。是否要做，以及是否与库表规则合成一个带 `scope` 维度的统一清单页（`sqlanalysis/rules/registry.py` 已把这个方向写进 docstring）。
2. **启用状态放哪**：D1 把它推迟到了「问题数旁边」，是否要做、做在库卡片还是问题清单页。
