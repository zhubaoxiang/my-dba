## Context

三块现成的东西决定了这个能力的形状：

- `apps/knowledge/llm.py`：`active_chat_provider()` / `build_chat_model()`
- `apps/sqlanalysis/schema.py`：`SchemaIndex` —— 从采集快照建的**真实**表/列/类型索引
- `apps/sqlanalysis/analyzer.py` + `rules/`：18 条规则，含 `unknown_table` / `unknown_column`

第三块是关键：**生成结果可以被项目自己验证**，而验证所需的正是第二块。这个闭环是这个能力与「随便接个模型让它写 SQL」的本质区别。

既有基调（本设计逐条对齐）：`sql-analysis` 的不落库、单条语句、执行必须显式触发、只读是服务端保证、未做校验必须说明原因。

## Goals / Non-Goals

- **Goals**：让使用者不必先查表结构就能拿到一条表名列名对得上的查询语句；把「生成结果可被验证」这件事做实
- **Non-Goals**：不做建表语句（另一半，独立变更）；不做多轮追问；不保存历史；不做自动粗筛选表；不改任何已有规则

## Decisions

### D1: 生成**任何** SQL，但绝不执行

- **Decision**：自然语言 → 一条 SQL。要查询给 `SELECT`，要改数据给 `UPDATE` / `DELETE` / `INSERT`，要改结构给 DDL。**只生成，不执行**。
- **Why**：README 的「做」清单本来就写着「帮使用者**写出**正确的建表语句与 SQL」，而「不做」里只写了「生产库变更执行」——**生成与执行是两件事**。已有基础设施也正好支持：试运行复用的 `/sql-analysis/execute` 对 DML/DDL 只出计划、绝不执行。
- **附带的好处**：那几条高危规则（`update_without_where` / `delete_without_where` / `drop_table` / `truncate_table`）正是为写语句准备的——只生成查询时它们全用不上。
- **修订（2026-10-10）**：初版决定「只做 SELECT，写需求不返回语句」。实测发现这会导致**最坏的结果**：提示词要求「只写查询」，于是模型读懂了 UPDATE 却只能勉强编一条 SELECT 交差，**而且不说明它没按你要求的做**。安静的错答比明确的拒绝糟得多，故放开为「什么都能生成，什么都不执行」。
- **保留的限制**：**建表语句没有结构校验**——表还不存在、没有快照可查，它的正确性无从自动验证（项目的库表规则吃的是采集快照的**结构**，不是 DDL 文本）。这一点必须写进文档与界面，不能让使用者以为它也「校验通过」了。
- **Alternatives considered**：维持只做查询、但识别出写需求时**明说**无法生成——比初版好（至少不静默），但把使用者本该拿到、且本来就在能力范围内的 UPDATE 推掉了。

### D2: 生成后用系统自己的规则验一遍，有问题让模型自修**一轮**

- **Decision**：生成 → 跑 18 条规则 → 若报出结构问题，把问题内容与**该库真实存在的表名**一并回给模型重生成一次 → 再跑规则 → 展示。**一轮为限，不是循环**。
- **Why**：NL2SQL 最容易错的地方是表名列名——模型会自信地编出 `user` / `order`，而库里叫 `app_user` / `orders`。而这恰恰是项目**已经能判**的一类问题。不自修就把「改表名」这步留给了使用者，而那正是这个能力本该替人干的活。
- **为什么一轮为限**：自修的收益在第一次最大（模型看到真实表名基本就能改对）；放宽到多轮会让成本与延迟不可控，且存在「越改越错」的风险。
- **自修后仍有问题怎么办**：如实展示剩余问题，并说明「已自修一轮仍未解决」——**不能因为修过就说成没问题**。

### D2b: 什么**不算**该自修的问题

- **Decision**：触发自修只认 `unknown_table` 与 `unknown_column`（「名字写错了」的直接证据）。
- **什么被排除**：`update_without_where` / `drop_table` 这类**高危告警不触发自修**。模型是**按使用者要求**写的——「把所有未研判的置为已通报」本来就没有 `WHERE`——让它去加一个 `WHERE` 等于**擅自改变语义**，使用者要的就不是那条语句了。
- **这条分界很重要**：自修负责「名字写错了」，**不负责「语句危险」**。危险只报出来给人看，不由系统替使用者改。

### D3: 表范围可选，不选给全库；超上下文**如实报错**，不截断

- **Decision**：页面给一个可搜索的表多选，但**不强制**。不选 = 全库结构；库中表多时界面提示建议缩小范围；结构真超出模型可承载范围时，接口报错并提示选表。
- **Why**：小库（十几张表）直接描述即可，不该强迫使用者先点几下；大库（几百张表）全量必然装不下。**截断后继续生成是最坏的选择**——它会安静地产出基于残缺结构的语句，而使用者以为模型看到了全库。
- **Alternatives considered**：自动粗筛（从描述抽词匹配表名/列名）——使用者无感，但筛错时「为什么没找到我的表」无法解释，等于把一个确定性的失败变成了看不懂的失败。

### D4: 试运行**复用已有端点**，不新增执行接口

- **Decision**：结果区的「试运行」按钮直接调既有的 `POST {SYS_NAME}/v1/sql-analysis/execute`。
- **Why**：它本来就接受任意 SQL + 数据源，边界（只读会话、行数上限、语句超时、DML/DDL 只出计划）已经论证并写在 `docs/sql-analysis.md` 里。再开一个执行接口等于把同一套边界抄第二遍，而两份边界迟早会不一致。
- **保持既有基调**：**不自动执行**。生成完只是给出 SQL，跑不跑由使用者按下按钮决定——这是 `sql-analysis` 定下的规矩（「会在真实的、可能是生产的库上执行语句，必须由使用者显式触发」）。

### D5: 复用一律走 `sqlanalysis` 的服务层，不绕过去 import 内部

- **Decision**：在 `apps/sqlanalysis/services.py` 增加 `load_schema_index()` 与 `analyze_sql()` 两个契约；`apps/nl2sql/` 只调这两个。
- **Why**：`architecture.md` 规定跨模块只读走对方模块的服务函数。该文件的 docstring 已经写明「后续若有别的对外只读需求，一律加在这里，不要开第二个入口」——本变更正是那条注释预期的使用者。
- **代价**：要把 `schema` / `analyzer` 的调用从视图层下沉到服务层。值得：视图层调内部模块本来就不该是别的模块的样板。

### D6: 校验只覆盖**结构**，这一点必须写在使用者看得见的地方

- **Decision**：结论区固定说明「本次校验只覆盖表名与列名是否存在、类型是否可比，**不覆盖查询逻辑是否符合你的本意**」。
- **Why**：这是本能力最容易被误读的地方。能力越像「智能」，越容易让人把「✓ 通过」读成「这条查询是对的」。而它实际只证明了**表名列名对得上**——条件写反、聚合口径错、时间范围错，它一概发现不了。
- **代价**：每次都要说一遍，略显啰嗦。但比让人拿着一条「验证通过」的错误查询去跑强。

### D7: 生成物不落库、只允许单条语句

- **Decision**：不建模型、不保存历史；多语句直接拒绝。
- **Why**：与 `sql-analysis` 完全一致——那个能力刻意不落库（「贴一条、看结论、改完就走」），多语句也直接拒绝（「多语句的执行语义很容易看漏，直接不支持比小心处理更安全」）。两个入口面向同一件事，边界不该有两套。

## Risks / Trade-offs

| 风险 | 影响 | 缓解 |
|------|------|------|
| **模型产出非法 SQL** | 拿不到可用结果 | 交给已有的解析器；解析失败时**如实报错**，不呈现半成品 |
| **自修把对的改错** | 结果反而变差 | 一轮为限；结果里标出自修前后的差异，使用者能看出它改了什么 |
| **自修被当成「已验证语义」** | 使用者过度信任 | D6 的固定说明；措辞限定在结构层面 |
| **生成的语句在真实库上很慢** | 试运行拖慢生产库 | 沿用已有的试运行边界（语句超时、行数上限）；生成本身不连库 |
| **大库结构塞不进上下文** | 生成失败 | D3：如实报错 + 提示选表，绝不截断 |
| **模型服务不稳定** | 偶发失败 | 读超时（`llm_timeout`，与解读一致），失败如实说明 |

## Migration Plan

无数据与部署变更：新增模块与页面，无模型、无 DDL。回滚即回退代码与路由注册。

`settings.py` 的 `INSTALLED_APPS` 需加 `apps.nl2sql`（无模型，仅为模块注册与将来扩展留位）。

## Open Questions

1. **建表语句那一半**：收益明确（接需求要建表是高频场景），但**生成结果无从自动验证**。若要做，需要先解决「怎么验」——可选方向是把生成的 DDL 用 `sqlglot` 解析成结构，再喂给现有的 7 条库表规则（它们吃的是结构，不是文本）。属独立变更，届时单独论证。
2. **多轮追问**：本次按单轮做。若实测下来「改一次描述重来」的体验不够，再评估是否引入会话状态——但那会与「不落库」的基调冲突，需要单独决定。
