# 首页（系统状态总览）

首页回答两个问题：**我该关注什么**，以及**为什么某个功能用不了**。

它不是看板：每条信息都指向一个动作（看问题 / 去采集 / 去配置 / 去提问）。对应模块：`src/apps/overview/`（**无数据模型**，只做跨模块只读聚合）。

## 页面结构

自上而下四段，**超出即滚动**：

```
┌──────────────────────────────────────────────────┐
│ ✓ 系统就绪：对话模型、嵌入模型均已配置              │  ← 缺什么才变色
├──────────────────────────────────────────────────┤
│  2/3          │ 7            │ 2              │  ← 概览数字带
│  已纳管的库·在线 │ 问题合计·高危 2 │ 知识库·32 篇文档 │
├───────────────────────┬──────────────────────────┤
│  ● prod_main [PG] 在线 │  PG 运维手册              │
│    9/100  12MB        │   32 篇 · 1,204 个检索块  │
│    99.2%  128         │   ▓▓▓▓▓▓▓▓▓░ 成功 31 失败1│
│    ╱╲╱ 近 24 小时连接数│   12 次提问 · 2 小时前更新 │
│    高2中5 · 采集于 3 分前│  [查看失败原因][去提问]   │
│  ● legacy 离线（红底） │                          │
│    连不上这个库        │                          │
│    OperationalError:..│                          │
│  [看问题][重新采集]    │                          │
├──────────────────────────────────────────────────┤
│ 最近刷新 17:42:30                              [刷新] │
└──────────────────────────────────────────────────┘
```

- **概览数字带**给一个总纲，首屏立刻有内容。「在线 2/3」这样的比值比单看某个库更早暴露问题
- **库数与在线数合成一格**：两者共用「总数」这一个数，分成两格是重复的。`2/3` 一个数就把规模和异常比例都说清了
- **库卡片网格（2 列）**：状态点、库名、类型标签、指标格、趋势、页脚动作
- **知识库卡片网格（2 列）**：规模、摄入状态堆叠条、使用情况
- 窄屏（`< lg`，即 1200px 以下）退化为**单列**

> 为什么接受滚动：库本来就可能接十几个，「一屏不滚」在多库时必然做不到。为少数场景把每张卡压到 150px（趋势图缩成小线、看不出形状），等于长期为一个偶发约束付代价。这个页面是**扫视**用的，滚一下很自然。

## 接口

`GET {SYS_NAME}/v1/overview` —— **一次返回首页所需的全部数据**。

前端自己拼至少要 6 个请求，其中「每个库的问题数」还是 N+1，所以做成单个聚合接口。

```json
{
  "readiness":       { "available": true, "ready": false, "missing": [{"item": "对话模型", "affected": "知识问答、SQL 分析的 AI 解读"}] },
  "summary":         { "datasource_total": 3, "online_total": 2, "issue_total": 7, "issue_high_total": 2,
                       "knowledge_base_total": 2, "document_total": 32 },
  "datasources":     { "available": true, "items": [ ... ] },
  "metrics":         { "available": true, "items": [ ... ] },
  "knowledge_bases": { "available": true, "items": [ ... ] }
}
```

**响应不含任何凭据**——数据源密码与模型 API Key 都不会出现在这里。

### `summary` 由已取回的块算出来，不额外查库

这样它与下面的卡片**必然一致**——分别取数的话，两次查询之间的变化会让「在线 2/3」和卡片上的状态对不上。

取不到的项记 `null`（前端显示 `—`），**不是 0**：`0` 是「数过了，一个也没有」，与「没数成」是两回事。比如指标块取不到时 `online_total` 是 `null`，不能显示成「0 个在线」。

## 取数口径

| 展示项 | 口径 |
|--------|------|
| 库的问题分级 | 该数据源**最近一次快照**的问题数（按级别） |
| 库的表数 / 采集时间 | 同一份最近快照 |
| 采集状态 | `collected` / `never` / `running` / `failed`（见下） |
| 库的在线与连接数 | `datasource_metric` 的**最新一行**（最多陈旧 5 分钟，见 [datasource-metrics.md](datasource-metrics.md)） |
| 库大小 / 缓存命中率 | 同上；命中率由**相邻两次采样的差值**算出，不是累计值 |
| 连接数趋势 | 最近 24 小时**在线**的采样点，**降采样到最多 48 个** |
| 知识库文档数 | 未删除的文档数 |
| 检索块数 | 未删除文档的 `chunk_count` 求和 |
| 摄入失败 | `kb_document.status` 为失败的条数，>0 时整卡标红 |
| 问答次数 | `qa_session` 中该知识库的会话数 |
| 最近更新 | 该知识库未删除文档的 `update_time` 最大值 |
| 就绪状态 | **只读本地配置**：对话模型、嵌入模型各是否有生效项 |

### 问题数为什么取「最新快照」而不是累计

同一处问题**每次采集都会重新产出一遍**，累加会让数字随采集次数虚增，而且**不指向任何动作**——使用者关心的是「这个库现在有多少问题」。

### 没有快照的库为什么不显示问题数

因为「**还没有数据**」与「**没有问题**」是两回事。没有快照时只显示采集状态（尚未采集 / 采集中 / 采集失败及原因）。这与 SQL 分析里「没能分析 ≠ 没有问题」是同一条原则。

### 采集状态的优先级

```
running（有任务在执行）
  → collected（有快照就算已采集，即便最近一次失败了——旧数据仍可用，
               失败通过 fail_reason 单独带出）
  → failed（没有快照且最近一次失败）
  → never（没有快照也没有失败记录）
```

## 就绪状态：只读本地配置，不探测外部服务

**刻意不探测 Qdrant、也不探测模型 API 的可达性。** 原因是探测 Qdrant 尤其危险：它的客户端超时取的是 `knowledge_llm_timeout`（**默认 60 秒**），向量服务一挂会把整个首页拖死——为一个提示把主页面卡住，代价远大于收益。

分工是清楚的：

- **配置缺失**是使用者自己能修的问题（去「模型配置」加一条）→ 首页提示
- **服务不可达**不是 → 由实际使用时的错误暴露（知识问答已有约定：向量服务故障必须与「无命中」区分开）

## 排序：把需要处理的浮上来

这个页面的职责是回答「我该关注什么」，所以：

- **库**：采集失败 → 未采集 → 采集中 → 已采集；同为已采集时按**高危问题数降序**，再按名称
- **知识库**：有摄入失败的 → 有未处理完的 → 其余；同级按名称

> 顺序会随状态变化，不固定。对入口页而言这是特性而非缺陷——按名称排序会让「一个有 5 个高危问题的库」和一堆正常库混在一起。

## 分块兜底：一块取不到不拖垮整页

任一模块取数失败时，只把**那一块**标记为 `available: false`，其余照常返回，并记 ERROR 日志。

首页是入口页，**部分数据取不到时整页报错是最糟的结果**——使用者连能用的部分也看不到了。取不到的那块在界面上如实标注为「暂不可用」，**不显示成没有数据**。

## 指标与趋势：形状看变化，颜色看危险

每张库卡片有 2×2 的指标格（当前连接 / 上限、数据库大小、缓存命中率、表数量）与一条连接数火花线。

### 趋势图自绘 SVG，不引图表库

项目现在没有图表库；为一条 100×34 的小线引入 ECharts 之类的几百 KB 依赖不成比例。自绘还能完全控制配色、粗细与渐变，与页面主题一致。**服务端把 24 小时的 288 个点降采样到最多 48 个**再返回——100px 宽的小图用不着那么多点。

### Y 轴自适应 + 颜色分档

折线**形状按数据范围自适应**：连接数若固定画到上限（100），`9/100` 会贴着底部、完全看不出变化。代价是微小波动会被放大——纯自适应会把 `9→10` 画得像翻倍。

因此**两个目标分开表达**：

- **形状**自适应 → 看趋势
- **颜色**按占上限的比例分档 → 报警

| 占上限比例 | 颜色 |
|-----------|------|
| `> 95%` | 红 |
| `80% ~ 95%` | 黄 |
| `< 80%` | 蓝 |

`9/100` 是安全的，`92/100` 该被一眼看到——**数字本身加同样的分档着色**，与折线颜色同口径。数字与颜色同屏并列，使用者能对照绝对值判断波动是否要紧。

### 指标历史不足时不画假线

趋势点少于 2 个（刚部署、采集进程刚起来）时显示「指标采集中…」，**不留白、不插值补点**。这条线是用来判断「最近是不是不对劲」的，画一条假的比不画更糟。

## 离线与「取不到」的呈现

| 情形 | 呈现 | 为什么 |
|------|------|--------|
| **最近一轮采集连不上** | 整卡红底红边，**完整**显示失败原因（不截断），**不显示**上一次的指标、不画趋势 | 过期的指标比没有指标更危险——`9/100` 看起来很健康，而库其实已经连不上了 |
| **指标块整块取数失败** | 卡片显示「指标暂不可用」，库的采集状态与问题数照常显示 | 「取数失败」与「还没采到」是两回事，不能混为一谈 |
| **该库还没有任何指标记录** | 指标格显示 `—`，趋势区显示「指标采集中…」 | 与「取到 0」区分开；首次部署后 5 分钟内就是这种状态 |
| **某项该方言取不到**（如 PG 16 以下的 `pg_stat_io`） | 该项显示 `—` | **不记 0**——「没有 IO 数据」与「IO 为零」是两回事 |

**每项信息都标明采集时刻**：快照的采集时间在页脚，指标的采集时刻在趋势区上方，都按新鲜度显示为「X 分钟前」。指标最多陈旧 5 分钟（采集间隔），不标出来使用者会以为它是实时的。

## 知识库卡片：三个有信息量的字段

除了原有的文档数与摄入状态，卡片增加：

- **检索块数**（`chunk_count` 求和）。「32 篇文档」是观感，**「1,204 个检索块」才是实际能搜到多少内容**——上传一篇 200 页 PDF 却只切出 3 个块，光看文档数看不出来
- **文档状态堆叠条**。摄入状态天然是**比例关系**，堆叠条比「成功 11、失败 1」的文字更直观
- **问答次数**。回答「这个知识库到底有没有人用」——建了 10 个、9 个没人问过是常见情况

界面用「检索块」而非「分块数」——它代表「能被搜到的内容单元」，更贴近使用者理解。

**空知识库**（0 篇文档）显示「还没有文档，问答时检索不到内容」，而不只是「0 篇文档」：要说的是**后果**，不是数字。

> **性能**：三组统计**各一次聚合查询**（`GROUP BY knowledge_base_id`），不逐个知识库查。

## 空状态

一个库都没接时显示虚线引导卡「还没有接入数据库 [去接入]」，没有知识库时同理。新部署的使用者打开首页看到的就是这个状态，留白等于什么都没说。

## 刷新

进入页面加载一次 + 手动刷新按钮 + 最近刷新时间。**不做轮询**——元数据变化得很慢（采集是手动触发的），指标也是 5 分钟才一轮，轮询纯属浪费。想看最新的指标，刷一下即可。

## 明确不做的

| 不做 | 原因 |
|------|------|
| **机器 CPU / 内存 / 磁盘** | 要读目标服务器本地文件并动用超级用户，代价与收益不成比例（[datasource-metrics.md](datasource-metrics.md)） |
| **指标告警与通知** | 连接数超阈值、离线持续 N 分钟时通知——属监控范畴，与本项目的边界冲突 |
| **趋势的范围切换 / 指标切换** | 当前只画 24 小时、只画连接数；库里存了 30 天，需要时再开 |
| **SQL 分析的任何数据** | 它刻意不落库（贴一条、看结论、改完就走），没有数据可展示；也不给它无数据的快捷入口，以免破坏「首页 = 状态总览」的定调 |
| **向量服务探测** | 见上：客户端超时 60 秒，会拖死首页 |
| **自动刷新** | 数据变化很慢 |
| **分页** | 页面接受滚动，首页不该有分页控件 |
