# 功能候选方向

> 这是**候选清单**，不是已承诺的排期。选定方向后按 OpenSpec 流程立项，把范围、边界与验收写进提案再动手。

## 判断基线

### 目标使用者

主要使用者是**写代码和测功能的人**，DBA 作为辅助；系统的边界见 [README 的「目标使用者与边界」](../README.md#目标使用者与边界)。

### 现有能力盘点

| 能力 | 解决的诉求 | 落点 |
|------|-----------|------|
| 分析数据库表 | 这个库/表长什么样、有没有坑 | [datasource.md](datasource.md) |
| 分析 SQL | 这条 SQL 写得对不对、会不会慢 | [sql-analysis.md](sql-analysis.md) |
| 说人话转 SQL | 按需求写出一条正确的 SQL | [nl2sql.md](nl2sql.md) |
| DDL 评审 | 这条建表/改表语句能不能安全执行 | [ddl-review.md](ddl-review.md) |
| 知识问答（RAG） | 报错、概念、用法是什么 | [knowledge-qa.md](knowledge-qa.md) |
| 首页总览与指标 | 我该关注什么、为什么某功能用不了 | [overview.md](overview.md)、[datasource-metrics.md](datasource-metrics.md) |
| 模型用量 | 模型调用花了多少 | 系统管理页 |

### 结论

**系统不缺分析能力，缺的是「把已有能力串起来」和「多环境视角」。**

- 已有能力大多是独立页面：贴一条 SQL → 看结论 → 离开；换个页面就要重新选数据源、重新找表
- 多库场景缺少全局视角：同名表在哪个库、测试库和生产库差在哪
- 面向测试人员的专属能力（造数）还是空白

因此下面的候选项以**复用现有基础设施**为主，而不是再造一套分析规则。

## 优先级总览

| 优先级 | 方向 | 改动面 | 一句话价值 |
|--------|------|--------|-----------|
| 第一梯队 | 结构对比（快照 diff） | 小（后端已完成，缺界面） | 测试库与生产库的结构差异一目了然 |
| 第一梯队 | 全局表/列搜索 | 小到中 | 「这张表在哪个库」不再是难题 |
| 第一梯队 | 测试数据生成（造数 SQL） | 中 | 给测试人员造数据，只生成不执行 |
| 第二梯队 | 问答 Agent 工具扩展 | 中到大 | 四个页面变成一个能调工具的「专家」 |
| 第二梯队 | 问题趋势与采集变更摘要 | 小 | 问题在变好还是变坏、这次采集改了什么 |
| 第二梯队 | 知识库缺料分析 | 中 | 让知识库靠真实提问变准 |
| 按需 | 审计日志 | 中 | 合规场景的记录要求 |
| 按需 | 数据源级权限 | 中到大 | 多团队时按库隔离可见范围 |
| 按需 | 数据字典导出 | 小到中 | 表结构可导出、可交接 |

## 第一梯队

### 1. 结构对比（快照 diff）

**要解决的问题**

开发与测试最常见的追问：「测试库和生产库结构差在哪？」「这次迁移有没有落下对象？」现在只能逐张表人工核对。

**现状基础**

- `differ.diff_snapshots()` 已完成纯计算对比（表的新增/删除、列的增删改、索引增删），见 `src/apps/datasource/differ.py`
- `GET /catalog/diff?snapshot_id=&compare_snapshot_id=` **接受任意两个快照**，并不限制同一数据源，见 `src/apps/datasource/views.py`
- 前端 `catalogApi.diff` 已封装，但**没有任何页面调用它**——后端完整，缺的只是入口

**做什么**

1. 结构对比页：选择两个快照（或两个数据源的最新快照），并排展示新增/删除/变更
2. 采集任务完成时自动与上一次快照对比，把变化摘要写进任务结果（新增表、删除列、索引变更各几处）
3. 首页库卡片标注「结构有变化」，引导使用者查看

**边界与注意**

- 对比的是**结构**，不是数据；页面必须写明
- 跨库对比时 schema 名可能不同（如 `public` 与 `app`），需要「按表名对齐」的选项，否则会全是假差异
- 表名大小写与方言差异（PostgreSQL / MySQL）要保持原样展示，不做归一化，避免把真实差异抹掉

**改动面**：小。主要是前端页面 + 一个便捷接口（按数据源取最新快照）。

### 2. 全局表/列搜索

**要解决的问题**

库一多，「`order_item` 这张表在哪个库」「哪个库有 `user_id` 这个列」就没有答案了。现在只能先选数据源、再选快照、再搜表名。

**现状基础**

- 表清单接口 `GET /catalog/tables` 已经是「快照 + 关键字」的搜索，但只能限定在单个快照内
- 各数据源的最新快照可以从 `metadata_snapshot` 取到

**做什么**

跨数据源搜索，结果按数据源分组：

- 搜索范围：表名、列名、表/列注释
- 结果项：数据源、表名、命中位置，点击直达表详情
- 可选扩展：问题全局搜索（按规则/表名），与问题清单页共用入口

**边界与注意**

- 先用「最新快照的 JSONB 直接查询」实现；库多了再评估落一张轻量搜索索引表（采集时写入），不要一上来就引入全文检索引擎
- 结果必须带「采集于何时」，避免使用者把旧结构当成现状

**改动面**：小到中。后端一个新搜索接口，前端一个搜索页或顶栏搜索框。

### 3. 测试数据生成（造数 SQL）

**要解决的问题**

测试人员需要按表结构造数据：字段类型、非空约束、主键唯一、外键引用顺序，手写既慢又容易违反约束。

**现状基础**

- 快照里有列类型/长度、可空性、主键、索引、外键（含 `ON DELETE` / `ON UPDATE`）
- 已有的 SQL 格式化与「只生成、不执行」口径可以直接复用

**做什么**

- 输入：数据源 + 表（可多选）+ 期望行数
- 输出：按依赖顺序排列的 `INSERT` 语句（先父表后子表）
- 确定性处理：类型与长度、`NOT NULL`、主键唯一、外键引用、可解析的 CHECK 约束
- 可选：固定随机种子以便复现；为字符串/金额/时间字段提供常用生成策略

**边界与注意**

- **只生成，不执行**——与 [nl2sql.md](nl2sql.md) 同一条边界
- 不能保证的必须如实标注：业务语义、复杂 CHECK、依赖应用层逻辑的字段。延续「取不到 ≠ 没有」的原则
- 生成结果不落库（页面离开即消失），与 SQL 分析一致

**改动面**：中。新增一个无模型的 stateless 接口与一个页面；核心是生成器与约束处理的单测。

## 第二梯队

### 4. 问答 Agent 工具扩展

**要解决的问题**

现在的问答 agent 只能查知识库、表结构、数据源概况与问题清单（见 `src/apps/knowledge/qa/tools.py`），还不能调用 SQL 分析与 DDL 评审。能力散在四个页面里，使用者要先知道「该去哪个页面」。

**做什么**

新增只读工具：

- `analyze_sql`：复用 18 条 SQL 规则，可选执行计划
- `review_ddl`：复用 DDL 评审的快照预演
- `compare_snapshots`：复用快照 diff

典型对话：「orders 表有什么隐患？帮我生成加主键的 DDL，并评审一下。」

**边界与注意**

- 工具**全部只读**、不执行任何写操作
- 结论仍由规则引擎产出，模型只做解读——延续 [sql-analysis.md](sql-analysis.md) 的分区原则
- 工具输出要有上限，避免把上下文塞满；来源必须对得上实际工具返回

**改动面**：中到大。工具本身是薄封装，主要成本在提示词、工具选择正确性与回归测试。

### 5. 问题趋势与采集变更摘要

**要解决的问题**

首页只有当前问题数，看不出「问题是在变好还是变坏」；采集之后也不知道这次结构改了什么。

**现状基础**

- `catalog_issue` 按快照留存，历史问题数可直接聚合
- 快照 diff 已具备（见第一梯队第 1 项）

**做什么**

- 库卡片或问题页展示问题数随快照的变化趋势
- 采集完成后给出「相对上次采集」的结构变更摘要

**改动面**：小。可与结构对比合并成一个迭代。

### 6. 知识库缺料分析

**要解决的问题**

知识库该补什么文档，目前靠管理员猜。

**做什么**

- 记录问答「无命中」的提问（可脱敏、只存问题文本）
- 提供「没帮助」反馈入口
- 管理员页面汇总高频无命中问题，作为补文档清单

**边界与注意**

- 只记录问题文本，不记录模型回答与使用者身份，除非另有明确需求
- 「无命中」与「模型答得不好」要分开统计，处置方式不同

**改动面**：中。

## 按需项（管理 / 合规）

### 7. 审计日志

记录「谁在什么时候对哪个库做了什么」：SQL 试运行、数据源增删改、规则调整、模型配置变更、用户与权限变更。

现有系统**没有审计能力**，试运行会真实连接目标库（只读会话），内部合规场景通常会要求可追溯。

注意：审计日志只追加、不提供修改入口；来源库名等敏感信息按部署要求脱敏。

### 8. 数据源级权限

当前只有两级角色（管理员 / 普通用户），**任何登录用户都能看到全部数据源与元数据**。多团队共用时，需要回答「谁能看哪个库」。

这会改动权限模型与大部分接口的取数范围，属于架构级改动，建议在确有需求时单独立项，而不是顺手加。

### 9. 数据字典导出

把表结构导出为 Markdown / `CREATE TABLE` / Excel，便于交接、评审与写文档。数据全部来自快照，不连接目标库。

## 明确不建议

以下方向与项目定位冲突或投入产出不成比例，列出来是为了避免反复讨论：

| 不做 | 原因 |
|------|------|
| 慢查询平台、巡检告警、SLA | 会把工具拖成运维平台，需要长期投入 |
| 上线审批流 | 项目定位是「帮人判断」，不是变更流程系统 |
| 容量规划、备份恢复、主从运维 | 已在 README 边界外 |
| 生产库变更执行 | 不可逆风险，已有能力一律只生成/只预演 |
| 引入全文检索引擎做全局搜索 | 当前数据量用 JSONB / 轻量索引表即可，先别加基础设施 |

## 落地时必须守住的口径

无论做哪一项，以下原则与现有模块保持一致：

1. **不执行写操作**：生成、预演、分析可以，执行必须由使用者自己完成
2. **结论不依赖模型**：确定性结论由规则引擎产出，模型只做总结与解读
3. **取不到 ≠ 没有**：采集失败、校验未覆盖、结构缺失都要如实标注，不能当成「没问题」
4. **误报比漏报贵**：宁可不报，也不要让使用者觉得清单全是噪音
5. **不落库的能力保持无状态**：新增能力默认不持久化输入输出，除非有明确的查询/协作需求

## 建议的推进顺序

1. 结构对比（最小成本补齐已有能力的短板）
2. 全局表/列搜索（多库场景的基础体验）
3. 测试数据生成（面向测试人员的差异化能力）
4. 问答 Agent 工具扩展（把四个页面串成一个专家，中期投入）

前三项都是复用现有基础设施，不引入新的外部依赖；第四项是定位升级，适合在前三项稳定后再做。
