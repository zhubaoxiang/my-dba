# 知识问答（RAG + 通用大模型）

把数据库相关的文档交给它，就能就着文档提问；文档里没有的，回退到通用大模型，并**明确告诉你这次没有文档支撑**。

对应模块：`src/apps/knowledge/`。

## 定位

服务于「这个报错 / 概念 / 用法是什么」这类问题。两条信息来路：

| 来路 | 内容 | 载体 |
|------|------|------|
| **知识库**（RAG） | 使用者自己上传/导入的文档 | 业务库正文 + Qdrant 向量索引 |
| **已纳管数据源** | 表结构（字段、索引、主键） | 采集快照，**不走向量库**，由工具实时查 |
| **通用大模型** | 模型自身知识 | 仅在无文档支撑时兜底，且必须标明 |

系统只对**数据库领域**的问题作答——这一点写在系统提示词里，也决定了它不接通用闲聊场景。

## 三种回答模式

`mode`：`1` 自动 / `2` 仅知识库 / `3` 仅通用模型（`utils/custom_enum.py` 的 `QaModeEnum`）。

| 模式 | 是否检索 | 无命中时的行为 |
|------|---------|---------------|
| **自动**（默认） | 是 | 回退到通用模型，结果里 `is_fallback=true` 并带 `note` 标明「未经文档支撑」 |
| **仅知识库** | 是 | 如实告知未找到，**不调用模型** |
| **仅通用模型** | 否 | 根本不检索，直接问模型 |

**为什么要有「无命中」这个概念**：技术问答里「检索不到却用模型常识作答」是**静默降级**——答案看起来有据，实际无据。所以：

- 默认 `auto` 让使用者不必理解 RAG 概念就能用，但回退时**必须显式标注**
- 允许强制 `knowledge_only`，需要严格依据时用它
- 「无命中」由**相似度阈值 + top-k** 共同判定，阈值可配置（见下）

模式的判定发生在**进入 agent 之前**——即「要不要用知识库」在编排层就定死了，不交给模型决定。

## 摄入链路

入口两个：`POST /kb-document`（上传文件）与 `POST /kb-document/import-url`（链接导入）。两者都立即返回文档记录，实际处理在后台任务 `ingest.run_ingest()` 里跑。

```
解析 ──▶ 算内容指纹 ──▶ 判重 ──▶ 切分 ──▶ 嵌入 ──▶ 写块(事务) ──▶ 写向量 ──▶ 置状态
                                        │                          │
                                    失败则一行不写            失败则补偿删除刚写的块
```

**解析**（`parse_file` / `parse_url`）

- 文件：后缀白名单 `.md .markdown .txt .text .pdf`，体积 ≤ 20MB，编码按 `utf-8 → utf-8-sig → gbk` 试解
- PDF：用 `pypdf` 抽文本；**纯扫描件没有文本层会明确报错**要求先做 OCR，而不是静默产出空文档
- 链接：`requests` 抓取 + BeautifulSoup 抽正文，剥离 `script/style/nav/header/footer/noscript`

**切分**（`split_text`）

- Markdown 按**标题层级**组织，块上记 `heading_path`（如 `索引/联合索引`），同一节内再按块大小切
- 非 Markdown 只按块大小切
- 相邻块保留**重叠窗口**（`chunk_overlap`）——块脱离上下文时答案会断章取义
- 段落过长时硬切（`_hard_split`）

**嵌入与写入**（`ingest`）——这是整个链路最需要小心的一步：

1. **先嵌入再落库**：嵌入失败时一行都不写，避免留下「有正文没向量」的半成品块
2. 嵌入结果条数必须与切分块数一致，否则报错
3. 事务内 `bulk_create` 块 + 更新 `chunk_count`
4. **写向量放在事务外**（Qdrant 不参与库事务），失败时用**补偿删除**回滚刚写入的块并把文档置为失败

> 为什么顺序是这样：跨系统的两步写入没有分布式事务可用，只能选一个方向让它「失败得干净」。先库后向量 + 补偿，结果是**要么两份都在，要么库里干净**——不会出现「向量指向不存在的块」。反过来的话，库回滚了而向量已经写进去，索引里就会留下永远检索不到正文的孤儿。

**失败一律落到文档状态上**（`status` + `fail_reason`），不向上抛——后台线程抛异常只会打一行日志，使用者在界面上看不到。

### 重复来源检测

按**内容指纹**（`content_hash`，正文的 SHA-256）判重，**不是**按文件名或 URL——换个文件名上传同一份文档也算重复，这正是要拦的情况。

两条路径的处理方式不同，因为**可交互性不同**：

| 路径 | 判重时机 | 命中时的行为 |
|------|---------|-------------|
| 上传文件（`create`） | **同步**——上传是同步的，内容当时就能拿到 | 未表态则返回 **4017**，给出 `on_duplicate=1`（跳过）/ `2`（覆盖）两个选项，由前端问一次；跳过时返回已有文档并带 `duplicated=true` |
| 链接导入（`import_url`） | **异步**——内容要抓取后才知道，那时已无法回头问使用者 | 默认**跳过并写明原因**，可选带 `on_duplicate=2` 覆盖 |

两种路径都**不静默产生重复内容**。

## 问答链路

接口是 `POST /qa-session/ask`，编排在 `qa/agent.py::answer()`。

```
取生效对话模型 ──▶ 模式判定 ──┬─ 仅通用模型 ──────────────────▶ 直接问模型
                              │
                              └─ 自动 / 仅知识库
                                     │
                            取生效嵌入模型（缺则报配置错误）
                                     │
                                 预检索 ──┬─ 无命中 ──▶ 仅知识库: 如实告知
                                          │             自动:  回退模型 + 标注
                                          └─ 有命中
                                                │
                                    构造工具 ──▶ agent 工具循环 ──▶ 组装来源
```

**预检索**（`_presearch`）：先用嵌入模型把问题向量化、检索一次，**用来判定「有没有命中」**。这一步的异常处理是关键——

> `VectorStoreError` **必须向上抛**，不能吞成「空结果」。否则「向量服务挂了」会被误判成「知识库里没有」，进而**静默回退到通用模型**，使用者拿到一个看起来正常、实则是降级的答案。

**agent 工具循环**（`_run_agent`）：`create_react_agent` + 工具集，模型自主决定调用哪些工具、调用几次。最大步数由 `agent_max_steps` 控制（`recursion_limit = steps * 2 + 2`）；达到上限中断时不抛出，而是返回一条说明本次中断的文本——**单轮失败不该让整轮问答失败**。

工具按请求构造（`qa/tools.py`），可用工具取决于请求带了什么：

| 工具 | 何时可用 | 作用 |
|------|---------|------|
| `search_knowledge_base` | 传了 `knowledge_base_id` | 检索知识库，返回带 `[1] [2]` 编号的片段（每段截 700 字符） |
| `get_table_schema` | 传了 `datasource_id` | 查最近一次采集快照：留空列出所有表（最多 50 张），传表名给字段与索引（截 1200 字符） |

**来源不允许由模型编造**：工具通过闭包把「本次实际检索返回的片段」写进 `collected` 列表，回答的 `sources` 从这个列表去重生成，**不是**从模型输出里解析出来的引用编号。模型在正文里写 `[3]` 而实际只检索到 2 条时，`sources` 依然是那 2 条。

**多轮上下文**：保留最近 `history_rounds` 轮（默认 6），超出直接截断，不做摘要（避免一轮问答里再插一次模型调用）。

## 关键设计决策

| 决策 | 理由 |
|------|------|
| **块正文以库内为准，Qdrant 只做可随时重建的索引** | 库内是唯一事实来源，软删除、审计、按内容检索 SQL 等既有约定全部照旧；Qdrant 数据丢了只是重建索引，不涉及正文。**点标识直接使用 `kb_chunk.id`**，因此索引可由正文纯函数式重建，也**不存在「向量写成功但标识回写失败」的漂移窗口**——`kb_chunk` 表刻意**不存** Qdrant 的点标识 |
| **单 agent + 工具调用，而非线性 RAG 链** | 使用者的真实问法常需要在多个动作间选择：「订单表里金额字段是什么类型」要查表结构，「这个隔离级别怎么配」要查文档，「这条 SQL 为什么慢」两者都要。线性链只能无条件检索一次，无法按问题选择 |
| **已纳管库的元数据不入向量库** | 表结构是**结构化且强时效**的数据——刚加的字段就该查到。入向量库会引入「快照过期」和「切分后语义失真」两个问题，而结构化查询本来就能精确回答「这张表有哪些字段」。代价是「哪个字段存订单号」这类模糊问法暂不支持（见「已知限制」） |
| **模型配置落库，且对话与嵌入分开配置** | API Key 是凭据，`conf.ini` 已被 git 跟踪，再塞密钥等于公开；模型与 base_url 属于会变的运维配置，落库可运行时切换、免重启（`CONF_ATTR` 在模块导入时载入）。**一条记录只承载一种用途**——现实里网关常常只提供对话模型，嵌入必然来自另一个服务，分开配置才能「一端没配不拖累另一端」 |
| **会话历史用项目自己的表，不用 langgraph checkpointer** | checkpointer 的存储格式是框架私有的，运维无法用 SQL 查询/清理，也不符合项目「继承 `AbstractTimeFiledModel`、软删除、显式 `db_table`」的约定 |
| **不做流式输出** | 项目所有接口统一返回 `{code, message, data}`，流式需要 SSE/分块传输，两者不兼容。为问答单独开一条不遵守统一格式的通道，代价大于收益 |

> 完整决策过程（含被否决的方案与实测数据）见 `openspec/changes/archive/2026-09-23-add-rag-knowledge-qa/design.md`。**注意该文档的 D1b 有一处已过时**——它写「在 `kb_chunk` 上回记 `qdrant_point_id`」，实际实现改为不回记，以本文与代码为准。

## 数据模型

| 表 | 说明 |
|----|------|
| `llm_provider` | 模型接入配置。**一条记录一种用途**（对话 / 嵌入），两类各自独立选生效；API Key 可逆加密 |
| `knowledge_base` | 知识库 |
| `kb_document` | 知识库中的文档（含摄入状态与内容指纹） |
| `kb_chunk` | 切分后的块，**正文以本表为准** |
| `qa_session` / `qa_message` | 问答会话与消息（含引用来源、调用过的工具、是否回退） |

`kb_chunk` 与 `kb_document` 的软删除是检索正确性的一部分：`retrieval.retrieve()` 回库取正文时过滤 `is_deleted=False`，因此**即使 Qdrant 侧残留了已删块的向量，也不会命中已删正文**——残留只影响检索候选集的大小，不影响正确性。

### 向量维度

向量维度**不放进配置文件**，而是写成 `apps/knowledge/models.py` 里的常量（当前 `1024`）。它必须与**三处**一致：

1. 嵌入模型的实际输出维度
2. `models.EMBEDDING_DIMENSIONS`
3. Qdrant 集合的 `size`

刻意不配置化的原因：三处不一致会表现为**难以定位的检索异常**，写成常量更容易在代码评审时被看见。写入前 `llm._verify_dimensions()` 会校验实际输出维度并给出明确报错。

**换嵌入模型 = 改这个常量 + 重建 Qdrant 集合 + 重新摄入全部文档**（集合的 `size` 不可改）。正文都在库内，第 3 步只是重算向量，没有数据风险。

## API

路径前缀 `{SYS_NAME}/v1`。

| 方法 | 路径 | 说明 |
|------|------|------|
| GET/POST | `/llm-provider` | 模型配置列表 / 新建 |
| GET/PUT/DELETE | `/llm-provider/{id}` | 详情 / 修改（`api_key` 留空表示不更换）/ 软删除 |
| POST | `/llm-provider/{id}/test` | 连通性测试（按用途发对应请求） |
| POST | `/llm-provider/{id}/activate` | 设为该类用途的生效配置 |
| GET/POST | `/knowledge-base` | 知识库列表 / 新建 |
| GET/PUT/DELETE | `/knowledge-base/{id}` | 详情 / 修改 / 软删除（连带清理文档与向量） |
| GET/POST | `/kb-document` | 文档列表 / 上传文件摄入 |
| POST | `/kb-document/import-url` | 通过链接导入 |
| POST | `/kb-document/{id}/reingest` | 重新摄入（仅链接来源；文件未落盘） |
| GET | `/qa-session` | 会话列表 |
| GET | `/qa-session/{id}` | 会话详情（含全部消息） |
| POST | `/qa-session/ask` | 提问 |

> ⚠️ 以上接口继承 `baseviews.AnyLogin`，**系统内不做任何认证与角色校验**。这意味着只要服务可达，任何人都能读写**模型 API Key 与知识库文档**。**服务只能部署在内网**——完整说明见 [architecture.md 的「认证与鉴权」](architecture.md#认证与鉴权)。

## 配置

`src/config/conf.ini` 的 `[knowledge]` 段（`utils/configure.py` 会自动加 `knowledge_` 前缀，即 `qdrant_url` 读出来是 `knowledge_qdrant_url`）：

| 配置项 | 说明 |
|--------|------|
| `qdrant_url` / `qdrant_collection` | 向量服务地址与集合名 |
| `llm_timeout` | 模型调用超时（秒） |
| `retrieval_top_k` / `similarity_threshold` | 检索条数与相似度阈值（余弦，低于阈值视为无命中） |
| `chunk_size` / `chunk_overlap` | 文档切分块大小与重叠窗口（字符数） |
| `agent_max_steps` / `history_rounds` | agent 最大步数、多轮上下文保留轮数 |

代码里都带默认值（`retrieval.py` / `ingest.py` / `qa/agent.py` 的 `_DEFAULT_*`），配置缺失或非法不会让功能崩掉。改动 `conf.ini` **必须重启进程**。

**模型与 API Key 不在这里**——它们落库，在「模型配置」页维护（见上文设计决策）。

## 部署前提

1. **Qdrant 服务**：`docker-compose.yml` 已含该服务（REST 6333 / gRPC 6334）。web 容器用 `network_mode: host`，因此应用侧连 `127.0.0.1:6333` 即可
2. **出网通道**：模型走的是公有云 API（对话与嵌入可以是不同服务商），服务需能访问它们；**内网有模型代理则把 `base_url` 指向代理**，无需改代码
3. **嵌入模型单独配置**：不少网关只提供对话模型（实测 `/models` 只返回对话模型、`/embeddings` 报 unsupported API name）。缺嵌入时「仅通用模型」仍可用，需要检索时才报出**可操作的提示**（4017 + 指明去「模型配置」加一条嵌入配置）

> 这三条都是**部署前提，不由应用层解决**。若不满足，故障表现为「调用超时」这类不易定位的现象。

## 实测踩坑

联调真实服务时踩到的，记在这里免得后人重走：

1. **`check_embedding_ctx_length` 必须关掉**。langchain-openai 默认开启，会先用 tiktoken 把文本切成 token id 再发；OpenAI 官方端点接受，但 OpenAI **兼容**端点（实测 SiliconFlow）要的是原文，直接返回 400「参数无效」
2. **`dimensions` 要显式传**。起初以为「开源服务多不支持该参数」而去掉它，实测结论相反：该服务原生输出 **4096 维**，且支持用 `dimensions` 截到 1024/1536/2048。集合 `size` 固定，靠它截到 1024 能省约 4 倍内存与存储。不支持的服务要么报错、要么忽略，两种都由 `_verify_dimensions` 兜住
3. **`base_url` 要填接口根（`.../v1`）**，不要带 `/embeddings` 后缀——客户端会自己拼，带后缀会请求到 `/embeddings/embeddings` 而 404
4. **Qdrant 客户端要 `trust_env=False`**。向量服务是内网组件，不该受开发机/服务器上的系统代理影响。实测踩过一次——本机开着代理时 httpx 会把发往内网地址的请求也丢给代理，代理连不通内网便回 502，现象与「向量服务挂了」完全一样。注意这只关掉向量客户端的环境探测；**模型调用走公网，那边仍需要代理**
5. **模型会把工具调用语法当正文吐出来**（实测 deepseek 间歇性复现）。两处缓解：① 不绑定工具的场景（`model_only` 回退、无知识库）改用**不含工具语义的提示词**——没有工具可调时提到工具会诱发模型编造调用语法；② 输出侧按特征剥离这类内容（`_strip_tool_markup`），全被剥离时给出可读兜底

## 已知限制

- **一次提问会多次调用嵌入服务**：实测「自动」模式 7 次、「仅知识库」5 次（1 次预检索 + 模型自行改写查询后的多次检索），耗时与费用随之上升
- **不做流式输出**：与统一响应格式冲突，一次性返回完整回答。agent 多步调用工具时首字节等待可能达数秒到十几秒
- **上传的文件不落盘**：因此「重新摄入」只支持链接来源，文件来源需重新上传
- **PDF 扫描件**抽不出文本，会明确报错要求先做 OCR
- **换嵌入模型需改 `models.EMBEDDING_DIMENSIONS`、重建 Qdrant 集合并重新摄入**（正文在库内，重建只是重算向量）
- **模糊问法暂不支持**：元数据不入向量库（见设计决策），「哪个字段存订单号」这类问题查不了
- **多轮上下文不做摘要**：超出 `history_rounds` 直接截断，长对话会丢失早期上下文
- **没有问答评测集**：检索质量目前靠人工试用判断

## 后续待办（尚未落地）
