# 分析数据库表（数据源纳管与元数据采集）

把 PostgreSQL / MySQL 数据源接进来，**只读**采集库表元数据——表结构、列定义、索引、主键与外键关联、行数与占用体积。采集一次之后可随时回看，不用每次去连库翻 `information_schema`。

采集完由内置规则给出一份隐患清单，回答「这个库有没有坑」。

对应模块：`src/apps/datasource/`。

## 数据表

DDL 见 `src/sql/pg_struct.sql`（全量）与 `src/sql/patch.sql`（增量），**本项目禁止 Django migration**。

| 表 | 说明 |
|----|------|
| `datasource` | 被纳管的数据源配置，密码可逆加密存储 |
| `metadata_snapshot` | 每次采集生成的不可变快照，原始结果存 JSONB |
| `collect_task` | 采集任务与状态 |
| `catalog_issue` | 库表健康问题清单 |
| `analysis_rule` | 分析规则的可配置元数据（启用开关 / 级别 / 阈值，见文末「进行中」） |

## 健康分析规则

规则由 `src/apps/datasource/rules/` **声明式注册**：每条规则 = 一个判定函数 + 一条 `RuleDefinition`（`code` / 名称 / 默认级别 / 适用层级 / 默认阈值）。规则以稳定的字符串 `code` 标识。

| 规则 code | 名称 | 默认级别 | 触发条件 | 对你意味着什么 |
|-----------|------|---------|---------|--------------|
| `no_primary_key` | 无主键表 | 高 | 表没有主键 | 无法按行定位，写进重复数据不容易发现 |
| `fk_without_index` | 外键缺索引 | 中 | 外键列没有以它为前导列的索引 | 按它做关联查询会全表扫描 |
| `duplicate_index` | 重复或冗余索引 | 中 / 低 | 索引列完全相同；或非唯一索引是另一索引的前缀 | 白占空间、拖慢写入；上线前删掉即可 |
| `unused_index` | 疑似未使用索引 | 低 | 索引使用次数为 0 且表行数超过阈值 | 只增加写入成本，可评估删除 |
| `big_table` | 超大表 | 中 | 行数或占用空间超过阈值 | 查询、加字段、加索引都会明显变慢 |
| `suspicious_column_type` | 可疑字段类型 | 中 / 低 | 用字符类型存时间；超长 varchar；大对象类型 | 字符串比较用不上时间运算与范围索引；大字段拖慢整表扫描 |
| `isolated_table` | 孤立表 | 低 | 既无外键，也未被任何表引用 | 可能是遗留表，改表前先确认是否还有人用 |

分析是**纯计算**：输入是采集快照，不访问数据库，因此同一份快照可用不同阈值反复重算，也便于单测。

> **怎么看级别**：级别是按**规则类型**静态指定的，不随表体量或业务重要性变化——一张 5 行的字典表没有主键和一张 5 亿行的订单表没有主键，报出来都是「高」。所以看到「高」先结合自己知道的情况判断轻重，别当成必须立刻处理的告警。引入体量维度是后续待办。

## 修复语句

问题清单里每条问题都附一条**可执行的修复语句**，把「发现了问题」接到「拿到能用的 SQL」。实现见 `apps/datasource/fixes.py`。

**两类分开陈列、各自标明来源**——这是这一节最要紧的一条：

| 来源 | 覆盖范围 | 怎么来的 |
|------|---------|---------|
| **由规则对象直接得出** | 9 个判定分支里的 7 个 | 规则手里有表名、列名、索引名，语句由**确定性模板**拼出。随问题清单一并返回，**不依赖模型** |
| **无唯一答案，需你决策** | 超大表（分区/归档）、大对象拆表 | 按需由模型给参考语句，结果另给一层底色并标「模型建议」 |

**为什么要分区**：模板生成的是**算出来的**，模型给的是**一种建议**。混在一起展示，使用者会同等信任——而后者可能只是众多可行方案里的一种。这跟项目一贯守的那条线是同一件事（`取不到 ≠ 没有`、`校验通过 ≠ 语义正确`）。

**每条语句都带风险前提**：删索引要确认无依赖、类型转换会因脏数据失败、代理键列名可能与现有列撞名。系统**不执行任何一条**（README 的边界：不做生产库变更执行）。

> **批量取出时前提必须跟着走**：一次复制多条时，每条前面都会带上它的问题说明与风险前提（作为 SQL 注释）。把前提丢掉、只拼出一段光秃秃的 DDL，是最危险的形态。

**判定依据不足时不给语句。** 目前只有一条落在这一类：`isolated_table`（孤立表）。它判的是「既没有外键，也没有被任何表引用」，而**大量正常库根本不建外键**——真机核对时 `覆羽51环境` 的 23 张表全被判成「孤立」，包括那些显然是业务表的（`tb_cases_project` / `tb_interface` / `tb_env`）。

「没有外键」与「没人用」之间隔着一整个业务上下文，而 `DROP TABLE` **不可逆**。把排查建议变成一条可直接执行的删除语句，是**把一个弱证据伪装成确定结论**——所以这条规则只留排查建议，不给语句。界面会说明为什么不给。

**只支持 PostgreSQL。** 生成出来的语句是要贴到目标库上跑的，而 `ALTER COLUMN … TYPE` / `bigserial` 这些在 MySQL 上是另一套写法——本仓库的真机环境没有 MySQL，写一套没验证过的 DDL 给人执行，恰恰是这个项目一直在防的事。非 PostgreSQL 的数据源会**明确说明不支持**，不静默降级。

### 索引名为什么单独存一列

`catalog_issue.fix_key` 存的是**生成修复语句所需的额外标识**，由各规则自己填：

- **索引类规则填索引名**——`column_name` 存的是列名列表，索引名原先**只出现在描述文字里**，不改结构的话 `DROP INDEX xxx` 就只能靠解析中文描述得出，那是脆的
- **可疑字段类型填命中的分支**（`char_time` / `long_varchar` / `large_object`）——这条规则有三个分支，可修的那两个语句形态完全不同，而表里没有 `data_type` 可分

### 为什么存「原料」而不是「成品语句」

存 `fix_sql`（语句本身）看似更省事，但那把模板当时的输出**固化**进库了——模板一改（比如索引名要加模式前缀），历史快照里的语句就是旧的，而使用者分不出哪些是旧的。**语句是派生物，不该存**。这与本模块吃过的那次教训同源：`analysis_rule` 存代码声明副本，结果规则改名后清单永远显示旧名字。

## 静音：让「我知道的问题」不再重复出现

问题清单**每次采集全量重算**，所以同一批问题会在每次采集后原样重现，把新问题淹掉。静音就是给它一个出口。

**粒度是「规则 + 表 + 列」**——精确到某一处。比它粗的「规则 + 表」会把后来新增的同类真问题一并静默掉；比它更粗的「整条规则」就是现成的「停用规则」，没必要再做一遍。

**为什么必须是一张独立的表**（`issue_mute`）：`catalog_issue` 的行每次采集都会全量重建（`_save_issues()` 直接 `bulk_create`），标记加在那上面**活不过一次采集**。这不是实现方式问题，是数据生命周期问题。

键取的都是**稳定值**：`rule_code` 是稳定标识，表名列名来自库。**不取 `target`** 这类拼接串——它的格式一变，静音就全失效了。

### 静音是**全局生效**的，不是「只在清单里隐藏」

被静音的问题在**问题清单与各处的问题统计**中都不再计入（首页问题合计、库卡片的分级问题数）。

只在清单里隐藏、首页照算，会立刻造出「**首页 7 条、清单 5 条**」——两处口径打架，而这个项目一路都在躲这个。实现上，两处的过滤走**同一个 `muted_filter()`**，不允许各写一遍。

**代价（明确接受）**：静音会让首页数字**变小**。这是它的本意，但界面必须说明——首页的问题合计上挂了「已静音的问题不计入」的提示，问题清单顶部常驻「已静音 N 条」的入口。

> **措辞用「静音」而不是「已处理 / 已修复」**：它**不表示问题消失了**，只表示不再报。用后者会让人以为修过了。

### 与「停用规则」的区别

| | 影响面 | 在哪 |
|---|---|---|
| **静音** | **精确到一处**（某张表的某个列上的某条规则） | 问题清单每条问题旁 |
| **停用规则** | **全局**（该规则以后哪个库都不跑） | 分析规则页的启用开关 |

两者都能让问题消失，但影响面差一个数量级。静音时界面上会点明这一点。

## 表的关系

表详情里有「关系」一区，两个方向分开列：**引用了哪些表**、**被哪些表引用**，都带列名与外键名，对方在同一快照里时可点跳过去。

### 「被引用」必须扫全库推导

外键是**单向声明**的：`orders.user_id → app_user.id` 只写在 `orders` 上，而 `app_user` 自身可能一个外键都没有，**却被十几张表引用**。只读本表会得出「无关系」这个**错误**结论。

所以这一侧由该快照的**全部表**反查得出（`services.table_relations()`，纯计算）。同名表跨模式时按「模式 + 表名」对齐，不会指错表。

### 为什么不画 ER 图

三条理由合起来是决定性的：

1. **项目一直不引图表库**——首页那条 100×34 的火花线都是自绘的，代码注释写着「为一条 100×34 的小线引入几百 KB 的依赖不成比例」。ER 图要引的图论库比这重得多
2. **全库 ER 图在本项目的真实库里不可读**——`ENV_TYPE=local` 那个库 105 张表，画出来是一团线
3. **实际要问的是「这张表跟谁有关」**，不是「整个库长什么样」。后者用列表答更快更准

「无关系」时明确说「没有任何外键关系」，**不留白**——空与「还没加载」在界面上长得一样。

## 安全说明

- 采集使用**独立只读短连接**，不复用 Django ORM 连接；PostgreSQL 连接显式 `set_session(readonly=True)`
- 采集只读系统目录，**不对目标库执行任何 DDL/DML**，也不支持在目标库上执行用户 SQL
- 数据源密码可逆加密存储（`utils/crypto.py`，Fernet），任何接口响应与日志都不含密码
- 加密密钥缺失时抛错，**不会回退为明文**

## 已知限制

- 采集任务走 `simple-background-task` 的**进程内内存队列**。进程重启后队列中的任务会丢失，需重新触发；任务状态以数据库 `collect_task` 为准（队列本身的说明见 [architecture.md 的「后台任务」](architecture.md#后台任务)）
- 多 worker 部署时，任务在接收该请求的 worker 进程内执行
- 「疑似未使用索引」依赖目标库的索引使用统计（PG `pg_stat_user_indexes`、MySQL `performance_schema`），取不到时跳过该规则并在快照的 `unavailable` 中留痕
- 单份快照的全部元数据存在一个 JSONB 单元格里，查询时整块载入并解析，**分页是"假分页"**。表数量上万后需要改为结构化明细表
- **快照没有保留策略**：每次采集整份复制，长期运行会持续占用存储
- MySQL 采集器尚未在真实 MySQL 上验证过（PostgreSQL 分支已端到端验证）

## 分析规则注册表

规则的**启用开关、严重级别、阈值**运行时可调，不用改代码发版。

**规则判定逻辑仍是代码**（不引入表达式引擎），只有元数据可配置：

```
代码声明（apps/datasource/rules/definitions.py）
  ├─ 规则清单、名称、说明、适用层级与默认值的唯一来源
  └─ 是「全集」——即使一条库记录都没有，规则照样生效
        ⊕ 叠加
analysis_rule 表
  └─ 只提供运行时改的三项：enabled / level / thresholds
```

**规则清单页也以代码声明为基底**：库里有记录只说明「这条被改过」，不决定它在不在清单里。所以清单**一打开就有内容**，与分析的取数口径一致——首页说 7 条，点进去也是 7 条。

库里**没有**某个 `code` 的记录时，分析用代码默认值；清单页展示默认值并把「恢复默认」置灰。第一次调整某条规则时后端为它顺手建行，**不需要任何前置动作**。

> 早期的「同步规则」按钮已随清单换基底一并移除：它原本的职责是「让页面有数据」，而这件事现在不再需要它。

**表里只有 `code` / `level` / `enabled` / `thresholds`。** 它曾经还有 `name` / `description` / `object_level` 三列，是「同步」动作刷新的**声明副本**。副本与声明并存会导致「在代码里给一条规则改名之后，清单里永远显示旧名字」（已起服务实测复现），故随 DDL 删除。清单里这三项一律取声明，只有那三项取库里的行。

### 规则管理接口

| 方法 | 路径 | 说明 |
|------|------|------|
| GET | `/analysis-rule` | 规则清单（分页），带级别/层级标签与「是否被调整过」 |
| PUT | `/analysis-rule/{code}` | 修改 `enabled` / `level` / `thresholds`（PUT 与 PATCH 同义）；库里没有则自动建行 |
| POST | `/analysis-rule/{code}/reset` | 恢复为代码声明的默认值；从未调整过的规则报参数错误 |

**规则以 `code` 定位，不用自增 id**：未落库的规则没有 id 可用，却必须可被修改。

两条刻意的约束：

- **不接受新建与删除**——规则来自代码声明，凭空建一条库记录没有对应实现；删掉库记录只会退回默认值，达不到「删除规则」的效果。要停用请改开关
- **名称、说明与适用层级不接受修改**——库里存的只是那三项覆盖值，改名字改说明无处生效

> SQL 分析规则在同一页的另一组里展示，但**只读**：它们没有覆盖机制，因此那一组不出现启用开关与级别下拉。接口见 [sql-analysis.md 的「规则清单」](sql-analysis.md#规则清单)。

### 规则集变化可被察觉

`metadata_snapshot.evaluated_rules` 记下**本次分析实际参与评估**的规则。与「当前启用数」不一致，即说明规则集在采集之后被改过——只比对当前配置是看不出来的。库表分析页会在两者不一致时给出提示。

> 停用一条规则**不影响历史数据**：已有快照及其问题清单保持不变，历史问题用自身行里快照下来的 `rule_name` 渲染，规则改名或停用后仍能正确展示。

### 阈值

阈值随规则走，存在 `analysis_rule.thresholds`（JSONB）。代码声明里的默认值与原先 `conf.ini` 的取值**逐一相同**（`10000000` / `10240` / `2000` / `10000`），行为不回归。

职责划分：采集参数是运行时基础设施配置，改完重启可以接受；分析阈值是业务策略，必须能运行时调整且可审计。

> **部署注意**：`patch.sql` 里与规则注册表相关的两条是——
>
> 1. `metadata_snapshot` 补 `evaluated_rules`（用于察觉规则集在采集之后被改过）
> 2. `analysis_rule` 删 `name` / `description` / `object_level` 三列
>
