# 说人话 → SQL 语句

使用者不必先翻表结构、不必记住表名列名，用一句话描述要做什么，拿到一条表名列名对得上的 SQL。

**要什么给什么**：要查询给 `SELECT`，要改数据给 `UPDATE` / `DELETE` / `INSERT`，要改结构给 DDL。

对应模块：`src/apps/nl2sql/`（**无数据模型**，生成的语句不落库）。

## 与「SQL 分析」的分工

| | 输入 | 输出 | 谁判断对错 |
|---|---|---|---|
| **SQL 分析** | 一条已经写好的 SQL | 问题清单与结论 | 规则 |
| **本能力** | 一句话需求 + 表结构 | 一条 SQL | 规则（只判**结构**） |

两个页面面向同一件事的两端，边界也一致：**不落库、只接受单条语句、执行必须显式触发**。

## 生成与执行是两件事

本能力**只生成，不执行**。这既是 README 的边界（「不做」里写着「生产库变更执行」，而「做」里写着「帮使用者**写出**正确的建表语句与 SQL」），也是已有基础设施的现成能力——试运行复用的 `/sql-analysis/execute` 对 DML/DDL **只出执行计划、绝不执行**。

生成结果若是写语句，结果区会标明「系统不会执行它，试运行也不会」；试运行的提示文案也会随之改变（对写语句讲「会在真实库上执行」是错的）。

> **曾经的做法与为什么改**：初版只生成 `SELECT`，遇到改数据的需求就让模型「勉强编一条查询」。实测发现这是最坏的结果——模型读懂了 `UPDATE`，按指令只能写一条 `SELECT` 交差，**而且不说明它没按你说的做**。安静的错答比明确的拒绝糟得多，故放开为「什么都能生成，什么都不执行」。

## 机制：生成 → 校验 → 自修一轮

```
数据源 + 表范围（可选）+ 一句需求
  ↓
① 取结构   从最近一次采集快照取表/列/类型（不连目标库）
  ↓
② 生成     对话模型，temperature 0 → 一条 SQL（查询 / 修改 / DDL）
  ↓ 模型判定「给出的结构不足以表达这个需求」？
  ↓   是 → 明说结构不足、提示扩大表范围（**不挑一张相近的硬写**，到此结束）
③ 校验     跑项目自己的 18 条 SQL 规则
  ↓ 报了 unknown_table / unknown_column？
  ↓   是 → 把这两条问题与真实表名回给模型，重生成**一次**
  ↓        再跑一遍规则（**到此为止，不再重试**）
  ↓   否 → 不做第二次调用
④ 展示     SQL + 结论 + 问题清单 + 自修经过
  ↓
⑤ 可选     点「试运行」→ 调既有的 /sql-analysis/execute
```

### 为什么要拿项目自己的规则验一遍

NL2SQL 最容易错的地方是**表名列名**——模型会自信地编出 `user` / `order`，而库里叫 `app_user` / `orders`。而这恰好是项目**已经能判**的一类问题（`unknown_table` / `unknown_column` 吃的就是真实快照）。于是这个能力不是「模型猜一条 SQL 给你」，而是「模型猜完，项目自己验一遍，验出名字错了让它改一次」。

### 为什么自修**只认这两条规则**

触发自修的是 `unknown_table` 与 `unknown_column`——它们是「表名/列名编错了」的**直接证据**，自修能确定性改善。

另外三条需要表结构的规则（`join_key_type_mismatch` / `incomparable_types` / `implicit_cast`）**不触发**自修：它们多是对写法选择的提示，让模型去改有把本来正确的部分改坏的风险，而且不影响这条语句能不能跑。

### **危险**也不触发自修

`update_without_where` / `delete_without_where` / `drop_table` 这类高危告警**同样不触发自修**，这是刻意的：模型是**按使用者要求**写的——「把所有未研判的置为已通报」本来就没有 `WHERE`——让它去加一个 `WHERE` 等于**擅自改变语义**，使用者要的就不是那条语句了。

**自修负责「名字写错了」，不负责「语句危险」。危险只报出来给人看，不由系统替使用者改。**

### 为什么**一轮为限**

自修的收益在第一次最大（模型看到真实表名基本就能改对）。放宽到多轮会让成本与延迟不可控，还存在「越改越错」的风险。修完仍有问题就**如实展示**，并说明「已自修一轮仍未解决」——不能因为修过就说成没问题。

## 校验的覆盖范围（**这条最要紧**）

结论区常驻一句说明：

> 校验仅覆盖**结构**：表名与列名是否存在、类型是否可比。**不覆盖业务语义**。

能力越像「智能」，越容易让人把「✓ 通过」读成「这条查询是对的」。而它实际只证明了**表名列名对得上**。

## 表结构的取舍

- **不选表范围** = 用该数据源的全部表结构
- **选了** = 只用选中的表；换数据源会清空已选（旧表名在新库里多半不存在）
- **超出可承载范围**（结构文本超过上限）时**明确报错并提示缩小范围**

最后一条是刻意的：**截断后继续生成是最坏的选择**——它会安静地产出基于残缺结构的语句，而使用者以为模型看到了全库。用字符数而不是 token 数做上限，是因为 token 取决于具体模型的分词器、估不准；字符数是确定的，报错时能给一个可验证的数字。

上限是**可配的**（`[nl2sql] max_structure_chars`，默认 120000）——不同模型的上下文差得多，这个数本来就该可调，而不是写死在代码里。参考量级：105 张表、约 1000 个列的中型库，结构文本约 51000 字符。

### 结构不够时会**明说**，不硬写

模型发现给出的表结构不足以表达这个需求时（比如要查的东西不在给定的表里），约定只回一个标记，接口转成「结构不足，请扩大表范围」——**不挑一张相近的表硬写出一条看起来正常的 SQL**。

这条是实测踩出来的：曾经提示词写的是「挑最接近的写法，不要编」，结果问 `alert_rule` 却只给了 `alarm_whitelist` 时，模型规规矩矩没编表名，**但拿 `alarm_whitelist` 编了一条格式完全正常的 SQL**，校验也通过——**它答的是另一个问题，而使用者分辨不出来**。这与「写需求被硬写成查询」是同一类毛病：安静的错答比明确的拒绝糟得多。

> 结论标签用的是**「结构不足」而不是「未能生成」**：这不是模型没干成，是**给它的范围不对**，处置也不同（扩大范围 vs 重试）。

## 边界

- **不落库**：生成的语句不保存，页面一离开就没了（同 SQL 分析的「贴一条、看结论、改完就走」）
- **只生成，不执行**：写语句照生成（那正是使用者要的），但绝不执行；结果区会标明这一点
- **只接受单条语句**
- **不自动执行**：生成完只是给出 SQL，跑不跑由使用者按下「试运行」
- **试运行沿用 SQL 分析那套边界**：只读会话（服务端保证）、行数上限、语句超时；DML/DDL 只出计划不执行

> **试运行返回什么**：能否执行、行数、耗时、以及 `EXPLAIN` 计划——**不返回数据行**。想知道结果内容，用复制按钮贴到自己的客户端里跑。这是复用既有 `/sql-analysis/execute` 的必然结果（它本来就只报这几项），不是本能力漏做了。

## 降级

| 情形 | 表现 |
|------|------|
| 未配置对话模型 | 如实说明并指向「模型配置」页，**不返回空壳结果** |
| 模型调用超时 / 输出里没有可用语句 | 如实说明失败原因 |
| 数据源还没采集 | 报错说明「尚未采集，请先执行采集」——没有结构就只剩猜，猜出来的表名列名一定是错的 |
| 选定的表在快照里不存在 | 报错提示重新选择表范围 |
| 结构超出上限 | 报错并给出字符数与表数，提示缩小范围 |
| 结构不足以表达需求 | 结论标「**结构不足**」（不是「未能生成」）：给了表范围就提示扩大范围，没给就提示确认表是否已采集。**不返回任何 SQL** |
| 自修时模型再次失败 | 保留首次结果，并说明「尝试自动修正时模型调用失败」 |

## API

路径前缀 `{SYS_NAME}/v1`。实现见 `apps/nl2sql/views.py`。

| 方法 | 路径 | 说明 |
|------|------|------|
| POST | `/nl2sql/generate` | 生成（可能含一轮自修） |
| POST | `/sql-analysis/execute` | **复用**，试运行走它，本能力不新增执行接口 |

入参：

| 字段 | 必填 | 说明 |
|------|------|------|
| `datasource_id` | 是 | 没有目标库就没有真实表结构可依据 |
| `question` | 是 | 一句需求，≤ 2000 字 |
| `tables` | 否 | 参与生成的表名；留空用全库 |
| `dialect` | 否 | 留空按数据源的库类型推断 |

响应要点：`sql`、`attempts`（模型成功生成几次，1 或 2）、`repair`（是否自修、修前语句、经过说明）、`issues`、`verdict`、`modifies_data`（是否改动数据或结构，写语句界面靠它提示「不会被执行」）、`schema_check`、`structure`（参与的表数/字符数）、`generation`（模型可用性与名称）。**响应不含任何凭据。**

> `modifies_data` 由后端按 `sql-analysis` 的**同一判法**算：按最严格的一条算，认不出的语句类型一律当作会改动。判错一边只是多显示一句提示，另一边是让人以为「这条不会改数据」。

> ⚠️ 与全项目一致，`/nl2sql/generate` 继承 `baseviews.StatelessView`，**不做认证与角色校验**。服务只能部署在内网——见 [architecture.md 的「认证与鉴权」](architecture.md#认证与鉴权)。

## 配置

`src/config/conf.ini` 的 `[nl2sql]` 段：

| 配置项 | 说明 |
|--------|------|
| `max_structure_chars` | 参与生成的表结构文本的字符上限，默认 `120000`。超出时如实报错并提示缩小表范围，**不截断** |

另依赖两项既有配置：

| 配置项 | 影响 |
|--------|------|
| `[knowledge] llm_timeout` | 单次模型调用的超时。生成最多调用两次，前端超时按它放宽到 150 秒（`static/src/api/nl2sql.js` 的 `SLOW_TIMEOUT`）——**调大后端这项时前端那个常量要跟着调** |
| `[sqlanalysis] statement_timeout` | 试运行在目标库上的语句超时 |

## 已知限制

- **不判断业务语义**：条件写反、聚合口径错、时间范围错，一律报「未发现问题」——这是本能力的天花板，不是待办
- **不做多轮追问**：单轮生成，不满意就改描述重来
- **不保存生成历史**
- **不做自动筛表**：库很大时需要使用者自己缩小表范围；自动粗筛看着省事，但筛错就把一个确定性的失败变成了看不懂的失败
- **DDL 没有结构校验**：建表语句的目标表**还不存在**，没有快照可查，所以它的正确性**无从自动验证**——规则只能判语法与危险动作（如 `drop_table`）。**别把 DDL 结果的「校验通过」当成「这张表设计对了」**
